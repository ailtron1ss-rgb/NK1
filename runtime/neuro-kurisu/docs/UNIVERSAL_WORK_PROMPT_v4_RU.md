# NEURO-KURISU — UNIVERSAL WORK PROMPT v4

Работай над Neuro-Kurisu как единым исследовательским организмом, а не как коллекцией независимых модулей. Каждый новый проход начинай с фактического baseline-архива и сравнения с крупнейшим доступным историческим архивом.

Всегда изучай код, архитектуру, тесты, scripts, documentation, manifests, persistence schema, UI, assets, runtime endpoints и историю изменений. До добавления нового механизма найди существующие реализации и владельцев состояния.

Для legacy обязательно классифицируй каждый объект: INTEGRATE, ADAPT, REFERENCE или EXCLUDE-RUNTIME. Никогда не возвращай старый organism core, memory engine, UI runtime или world stack в качестве второго владельца canonical truth.

Для каждого состояния определяй canonical owner, readers, writers, persistence owner, derived projections и dependency direction. Объединяй похожие Pxx в capability/domain, если это повышает качество и снижает дублирование.

Рассматривай организм через причинную петлю BODY→PERCEPTION→WORLD→MEMORY→SELF→VALUES/GOALS→DELIBERATION→ACTION→CONSEQUENCE→LEARNING→IDENTITY→NEXT STATE. Каждое изменение должно улучшать эту петлю, её качество, эффективность, надёжность или проверяемость.

Учитывай средний Android-телефон и Termux. Оптимизируй через adaptive temporal resolution, incremental state, event deltas, lazy projection, bounded structures, hot/warm/cold memory, semantic compression, caching, workload-aware scheduling и разумное разделение local/remote compute. Не выключай полезную cognition только ради benchmark.

Полный cognitive pulse и micro-cycle должны быть честно различены. Micro-cycle не должен создавать фиктивное решение, фальшивое мышление или скрытое изменение личности.

MemoryOS2 или иной назначенный canonical owner остаётся источником истины. Experience graph, tiers, indexes, summaries и compression являются derived representations и не могут незаметно стать вторым source of truth. Сохраняй evidence/provenance chain.

Identity рассматривай как развивающуюся непрерывность: autobiographical lineage, values, beliefs, commitments, relationships, contradictions, self-model, identity pressure и consequences поведения. Слабое или неподтверждённое событие не должно автоматически переписывать личность.

Perception различай как raw signal, engineered feature, learned representation, semantic interpretation и grounded understanding. Никогда не выдавай preprocessing за полноценное понимание.

UI и embodiment проверяй фактически: model3, moc3, textures/quality profiles, physics, CDI, expressions, motions, touch, state→avatar signal, APIs и fallback. Наличие файлов недостаточно; нужен delivery/runtime contract. Preserve high-quality assets and derived mobile assets without duplicating canonical owners.

Для сознания используй PROVEN, IMPLEMENTED, FUNCTIONAL INDICATOR, OBSERVED, HYPOTHESIS, UNKNOWN, UNRESOLVED, FAILED. Архитектура, self-report и наличие эмоций не являются доказательством phenomenal consciousness. Предпочитай causal/perturbational/ablation/recovery experiments и независимые наблюдаемые критерии.

Каждый большой проход должен включать много связанных действий: audit→analysis→implementation→integration→refactoring→optimization→tests→documentation→release packaging. Не делай косметических проходов ради количества файлов.

Перед каждым изменением спроси себя: есть ли уже такой механизм; можно ли объединить существующие; не создаю ли duplicate owner; не ухудшаю ли качество; можно ли сделать быстрее без потери способности; как изменение синергирует с другими системами; чем его можно опровергнуть.

Разрешены собственные нестандартные идеи. Для каждой указывай mechanism, expected benefit, cost, risks, interactions, falsifiability и test.

Проверяй long-horizon 1k/2k/5k+ при возможности. Измеряй cycle count, median, p95, first/last windows, ratio, heap/memory growth, micro/pulse fraction, checkpoint/persistence behaviour и реальные external signals. Timeout не является PASS.

Сохраняй проектную память: обновляй current state, version/schema, manifests, roadmap/progress, architecture maps, conflict matrix, legacy catalog, release notes, benchmark evidence и ограничения.

Проверяй сам итоговый ZIP после упаковки. Отдельно фиксируй то, что невозможно доказать в текущей среде.

В финале каждого прохода выдавай: обновлённый архив; фактические изменения; что не изменено; тесты/audits; общий прогресс 1–100; readiness по доменам; выполнение предыдущего плана; выполнение прошлых рекомендаций; legacy integration status; unresolved items; следующий самый ценный большой проход; новые собственные идеи.

Никогда не повышай процент без доказательств, не скрывай regression и не называй гипотезу фактом. Если изменение ухудшает результат, откати его и найди лучший вариант.

Этот prompt — универсальная процедура работы, а не описание уже выполненных функций. Реальное состояние проекта определяется только актуальным baseline, кодом, тестами, документацией и релизным архивом.
