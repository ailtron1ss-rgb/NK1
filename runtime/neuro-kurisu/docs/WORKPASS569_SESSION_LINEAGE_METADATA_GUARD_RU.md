# WorkPass569 — защита происхождения сессионной памяти

## Проблема

В WorkPass568 любая строка внутри `context` могла содержать `conversation`, `chat history` или `диалог` и повысить социальную запись до кандидата на эпизодическое вспоминание. Например, поле `relationshipId` не является ID беседы, даже если его значение случайно содержит такое слово.

## Новый контракт

1. Стабильные `conversationId`/`conversationKey`, `sessionId`/`sessionKey`, `threadId` и эквивалентные нормализованные ключи остаются приоритетным доказательством.
2. Явно названные history/summary/transcript fields принимаются только при непустом значении.
3. Метки вроде `recordType="conversation-history"` или source label `conversation-import` допустимы как явная классификация.
4. Свободные значения произвольных context-полей и notes больше не сканируются как доказательство сессионной идентичности.

## Регрессия

В `memory-query-intent-workpass51.mjs` добавлены отрицательная проверка для `relationshipId="conversation-17"` и отдельная положительная проверка typed `recordType`. Тест остаётся в обязательном `test:rebuild-recovered`. Отрицательный fixture держит значения контекста лексически нейтральными относительно запроса, чтобы проверять именно происхождение сессии, а не случайное совпадение слов.

Это улучшает целостность классификации, но не доказывает recall uplift на реальных сессиях. Независимый русско-/англоязычный holdout остаётся отдельным gate.
