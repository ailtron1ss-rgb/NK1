# WorkPass340 — мост Hexis HMX 1.7 в каноническую память NK1

Дата: 2026-10-25  
Целевая ветка: `integration`  
Рабочая ветка: `workpass340-hexis-canonical-memory-bridge-20261025`

## Реализовано

- Добавлен адаптер экспорта NK1 → HMX 1.7. Он нормализует идентификаторы и ссылки записей, сохраняет происхождение нативных объектов и включает в экспорт явное предупреждение: автоматическое удаление чувствительных данных не выполнялось.
- Добавлен узкий Hexis → NK1 projector. Он пишет через существующий `MemoryFabric`, а не меняет файл состояния напрямую; связи проецируются в существующий `SemanticMemoryGraph` только для импортированных записей с известными endpoints.
- Импорт допускается только для принятого этапа `port + additive`. Содержимое пакета проверяется до первой канонической записи. При ошибке применяется компенсация новых записей и графовых изменений; этап остаётся доступным для контролируемого повтора.
- HTTP-путь различает `accept` и `apply`: подтверждение не изменяет память, применение возвращает receipt и должно быть идемпотентным при повторном запросе.
- Добавлены регрессии экспортера, канонического projector и серверного сценария. Создан отдельный Node.js 24 CI workflow.

## Границы интеграции

- NK1 остаётся единственным владельцем текущего runtime, памяти и когнитивного цикла.
- Этот проход не запускает Hexis Python/PostgreSQL runtime и не применяет миграции Hexis к базе NK1.
- Identity, цели и другие секции, для которых ещё нет полного канонического projector, должны оставаться отложенными; наличие секции в HMX не означает её импорт.
- Предупреждение об отсутствии автоматической редактуры обязательно; адаптер не заявляет, что экспорт обезличен.

- Исправлен дефект P68: ранее цикл обходил только активные цели, поэтому ветка возврата из `paused` была недостижима. Теперь обычные цели проходят жизненный цикл повторно, а цели `source: external` остаются заблокированными до `activationApproved: true`. Повторная активация также соблюдает лимит в четыре активные цели.
- Повторный вызов projector для уже применённого этапа теперь возвращает сохранённый receipt до проверки `accepted`, не выполняя новую запись.
- При импорте статусы памяти отображаются консервативно: `quarantined`, `archived`, `deleted`, `forgotten`, `rejected`, `inactive` и `superseded` не становятся доступными убеждениями; неизвестный статус остаётся `unknown`. Внешняя метка `fact` также не может повысить запись до NK1-подтверждённого факта: она импортируется как `belief`.
- Исправлена некорректная регулярка управляющих символов в `OutcomeVerificationService.ts`, из-за которой Node.js 24 прекращал загрузку runtime ещё до HMX-тестов.

## Проверка

CI разделён на независимые этапы из `runtime/neuro-kurisu`:

- `npm run audit:hexis` — блокирующие регрессионные тесты экспортера, projector, server smoke и UI wiring.
- `npm run typecheck` — отдельная диагностическая задача, потому что первый exact-head прогон остановился на общем typecheck и не дошёл до Hexis-тестов. Он сообщил множество ошибок по проекту, в том числе несколько локальных проблем строгой типизации этого моста. Для локальных проблем добавлены `.d.mts`-объявление и безопасные сужения типов; повторный результат ещё должен подтвердить исправление.

Статус на момент обновления: первый прогон **FAILED** до запуска Hexis-регрессий; workflow изменён так, чтобы тесты запускались независимо от общего typecheck. Новый exact-head результат пока не подтверждён. До успешного прогона `audit:hexis` мост нельзя считать проверенным или production-ready.
