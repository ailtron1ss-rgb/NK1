## 2. Диагноз: три аспекта есть, замкнутого контура нет

### 2.1. Что построено

- **Память.** Один заявленный владелец (`MemoryOS2`), вокруг него `MemoryFabric`, `ExperienceContinuumFabric`, `HippocampalMemorySubstrate`, `CanonicalMemoryLifecycleAuthority`, `NegativeSpaceMemory`, `MemoryRetentionEconomy`, `MemoryCausalEconomy`. В `MemorySubsystemRuntime` физически создаётся **25+ компонентов памяти**; в `memory/` — 5 231 строка, в `developmental/` — 11 573 строки. Есть 132 профильных теста.
- **Автономность.** `AgencySubsystemRuntime` владеет `SelfProjectEngine`, `AgencyDeliberationEngine`, `CognitiveBudgetManager`, `CognitiveQuorumEngine`, `AutonomousProjectExecutor`, `P67AutonomousGoalGenesis`, `P68GoalEcology`, `B306/B333/B334/B335/B336`-гейтами, `LongHorizonAutonomyController`, `SelfDirectedLifeOrchestrator`, `AutonomousSocialInitiativeEngine`, `LiveSelfImprovementSupervisor` и журналом decision receipts. 39 профильных тестов.
- **Саморазвитие.** `P36AutonomousSelfDevelopment` (882 строки) умеет: выбрать область развития, оценить инвестицию, открыть цикл, выпустить задачу, собрать campaign plan, записать внешнее свидетельство с CI и holdout, продвинуть/откатить. `P23LearningEngine` (2 067 строк) содержит population search, Pareto-архив, независимого оценщика, подписанные shadow-свидетельства. 62 теста по learning, 27 по skills.

### 2.2. Десять корневых дефектов

1. **Дублирование владельцев состояния.** «Один канонический владелец» декларирован, но `MemorySubsystemRuntime` держит 25 компонентов с собственным состоянием, `AgencySubsystemRuntime` — 20+. Каждый snapshot/restore — отдельный контракт, значит рассинхронизация при рестарте почти неизбежна.
2. **Память остаётся лексической.** `vectorize()` в `MemoryOS2` — 48-мерный FNV-хеш, а не семантическое представление. Диагностика гибридного поиска прямо содержит `semanticVectorUsedForRanking: false`. Embeddings включаются только opt-in и **не участвуют в ранжировании**.
3. **Нет доказанного uplift.** Semantic-benchmark по контракту всегда `promotion.allowed=false`; проект фиксирует `recallDelta=0`. Это честно, но означает: улучшать память пока нечем измерять.
4. **Автономия — это набор планировщиков, а не один цикл.** `AgencyDeliberationEngine` — 123 строки, где сила «своего» решения считается эвристикой `0.45 + intrinsic*0.4 − external*0.15`. Это не модель арбитража, а формула.
5. **Разрыв причинного кредита.** Issue #865 (открыт 13.11) фиксирует: внешний postcondition принимается, но `canonicalTemporalCredit.pending` для точного `decisionId` остаётся неразрешённым. То есть обучение по последствиям в этом пути не замыкается.
6. **Авторство смешивалось с выбором.** Исправлено в #1157: выбор действия создаёт bounded pending decision, кредит — только по `executed: true`. Но P0-фиксы памяти и self-authorship ещё в Draft #1153, не в каноне.
7. **Самоулучшение не подключено к исполнению.** `TheInventionLoop` не вызывается из Core/Agency; `P53DevelopmentalSelfModificationLab` не создаётся в проверенных entrypoints; `SourceGraph`/`SelfModificationGuard` в текущем дереве отсутствуют. Саморазвитие пока — лаборатория, а не контур.
8. **Слишком много веток и PR.** 1 140 веток, из них 106 «memory», 76 «cognit», 20 «autonom», 19 «learning», 35 «affect». Значительная часть работы существует вне канона; интеграция дороже, чем разработка.
9. **Реестр аспектов устарел.** `aspects.v1.json` — снимок 06.11 на старом SHA. Его статусы нельзя использовать как доказательство зрелости; это признано в `AGENTS.md`.
10. **Нет северной метрики.** Есть десятки proxy-показателей, но нет одной тройки: качество памяти → качество решений → подтверждённый прирост. Без неё любой «прогресс» — это количество модулей.

### 2.3. Целевая формула

> **Память** хранит проверяемый опыт → **Автономность** превращает внутренний сигнал в разрешённое действие с receipt → **Саморазвитие** меняет поведение только при независимом подтверждении и умеет откатиться.

Все три аспекта должны сходиться в одном `decisionId` и одном наборе свидетельств. Это и есть главный принцип плана: **не добавлять новые механизмы, а замыкать существующие и удалять дубли**.

## 3. Память: от «много компонентов» к одному проверяемому хранилищу

### 3.1. Фактическое состояние

**Сильные стороны.** `MemoryOS2` — действительно содержательный владелец: стабильные ID, `contentHash`, битемпоральные интервалы (fact/assessment/prediction), provenance-классы (device/external/user/agent/derived/simulation), эпистемический статус (fact/belief/hypothesis/unknown/quarantined), тумбстоуны, бюджеты байт, restore-диагностика (12 счётчиков), явный `forget`, конфликт-скан, RRF-гибрид BM25 + coverage + fuzzy + entity + graph-temporal, answerability-gate с отказом от ответа. Это выше среднего для исследовательского проекта.

**Слабые места, подтверждённые кодом:**

1. `vectorize()` — 48-мерная хеш-проекция. Это **не** embedding; использовать её как семантику нельзя.
2. Семантический индекс существует, но `semanticVectorUsedForRanking: false`; embeddings — opt-in preview-путь, а не компонент ранжирования.
3. Любой semantic-benchmark возвращает `promotion.allowed=false` по контракту, даже при прохождении гейтов.
4. Ранжирование живёт в одном 2 764-строчном файле; изменение весов не изолировано и не версионируется как политика.
5. 25 компонентов памяти в одном runtime — 25 независимых snapshot/restore-контрактов.
6. Нет единого типизированного инвентаря: эпизодическая, семантическая, процедурная, автобиографическая, социальная память размазаны по `memory/`, `developmental/`, `cognition/`.
7. Холодная/тёплая residency и eviction описаны, но влияние на ranking и на стоимость retrieval не измерено на целевом корпусе.
8. Нет опубликованного замера на 10k записей: latency, RAM, доля попаданий в кэш.

### 3.2. План по памяти (M1–M28)

Каждый шаг: **что меняем → где → критерий приёмки**.

**Волна M-A. Целостность и один владелец (P0)**

- **M1. Зафиксировать truth baseline.** Снять SHA `workpass70-source`, список всех state-файлов и владельцев, полный manifest памяти. Артефакт: `docs/engineering/MEMORY_TRUTH_BASELINE.md` + JSON. Приёмка: каждый writable-путь имеет одного названного владельца; файлов-сирот нет.
- **M2. Довести и влить #1153.** Проверить четыре P0-фикса: коллизии caller-ID, пересчёт байт после обратных связей, нормализация revision-массивов, сохранение valid-time границ. Приёмка: exact-head тесты + restore round-trip; PR выходит из Draft и попадает в канон.
- **M3. Типизированный инвентарь памяти.** Ввести `MemoryKind = episodic | semantic | procedural | autobiographical | social | spatial | negative` и обязательное поле `kind` в канонической записи. Приёмка: миграция старых записей, отсутствие `unknown` после миграции, тест на restore.
- **M4. Один snapshot-контракт.** Свести 25 компонентов к одной версионированной проекции `MemorySnapshotV8` с явными секциями. Приёмка: один restore-тест на все секции; любая отсутствующая секция — fail-closed, а не «пусто».
- **M5. Инварианты записи.** Проверить атомарность: запись + проекции + индексы + receipt. Приёмка: fault injection между этапами не оставляет полу-состояния; после рестарта либо всё, либо ничего.
- **M6. Полный `forget`.** Явное забывание должно вычищать store, проекции, кэш, embeddings, snapshot и экспорт. Приёмка: тест «после forget и рестарта запись не воскресает».
- **M7. Идемпотентность replay.** Повторное применение того же события не создаёт дубль и не увеличивает счётчики. Приёмка: дубликат по ID и по `contentHash` даёт ровно один эффект.
- **M8. Restore hostile input.** Accessor/Proxy/NaN/Infinity/oversize/дубликаты/циклические ссылки. Приёмка: ни один кейс не мутирует состояние частично.

**Волна M-B. Retrieval как измеримая политика (P0/P1)**

- **M9. Вынести ranking policy в отдельный версионируемый модуль.** `MemoryRankingPolicyV1` с весами BM25/coverage/fuzzy/entity/graph-temporal/intent. Приёмка: веса не зашиты в `MemoryOS2`; политика сохраняется в snapshot и попадает в отчёт эксперимента.
- **M10. Заморозить baseline.** BM25-only и текущий hybrid на неизменяемом корпусе. Приёмка: воспроизводимый manifest с хешем корпуса и seed.
- **M11. Собрать независимый RU/EN holdout.** Семьи задач: answerable, unanswerable, temporal revision, contradiction, personal preference, memory-to-action. Приёмка: нет near-duplicate и session leakage; provenance и разрешения приложены.
- **M12. Ввести метрики полного набора.** Recall@5/10, MRR, nDCG@10, task success, false recall, stale-fact use, contradiction rate, abstention precision. Приёмка: один отчёт на 5 paired seeds с per-case результатами.
- **M13. Подключить embeddings к ранжированию под флагом.** Не заменять lexical, а добавлять сигнал с весом и порогом. Приёмка: ablation lexical / semantic / hybrid / hybrid+rerank на одном бюджете.
- **M14. Настоящий локальный embedding-provider.** Зафиксировать модель, версию, hash, latency; loopback-only по умолчанию. Приёмка: индекс строится полностью, иначе эксперимент `skipped`.
- **M15. Снять запрет на промоушен по заслугам.** Разрешить `promotion.allowed=true` только при положительном lower confidence bound и не-росте false recall на независимом holdout. Приёмка: negative-control прогон не продвигается.
- **M16. Reranker как отдельный слой.** Cross-encoder/локальный reranker поверх top-N, с бюджетом latency. Приёмка: прирост nDCG не ниже заранее объявленного MDE, иначе reject.
- **M17. Temporal correctness.** Запросы «на момент T», superseded-факты, противоречия. Приёмка: stale-fact rate ниже baseline; противоречие создаёт dispute, а не перезапись.
- **M18. Пространственная и негативная память.** Привязать `GroundedSpatialMemoryBridge` и `NegativeSpaceMemory` к общему `kind` и к общему answerability-gate. Приёмка: пространственный запрос не отвечает без кадра сцены; негативная память не подмешивается в факты.

**Волна M-C. Стоимость, консолидация, непрерывность (P1)**

- **M19. Замер на целевом корпусе.** 1k / 10k / 50k записей: p50/p95 latency, peak RAM, размер индекса. Приёмка: отчёт с железом (Dell G3, i5, GTX 1650) и с Poco M7 Pro для мобильного профиля.
- **M20. Residency без скрытых мутаций.** Холодные записи не меняют ranking; прогрев — явная операция. Приёмка: тест «одинаковый запрос до и после прогрева даёт тот же порядок, если политика не менялась».
- **M21. Eviction с regret.** Бюджет байт, вытеснение по полезности, журнал witness-записей. Приёмка: mean eviction regret измерен и не растёт после консолидации.
- **M22. Консолидация эпизод → семантика.** Явный ночной контроллер, идемпотентный, с ограничением батча. Приёмка: после консолидации число эпизодов падает, ответы на holdout не деградируют.
- **M23. Дедупликация и слияние.** Одинаковый `contentHash` — один факт; близкий — revision, а не дубль. Приёмка: метрика duplicate rate и отсутствие роста store после replay.
- **M24. Валидация HMX/HeXis/Neko-мостов.** Один write-owner, полная схема, явный список deferred-сущностей. Приёмка: bridge не может писать в обход `MemoryFabric`.
- **M25. Privacy-границы.** Секреты и приватные строки не уходят в embedding-провайдер; redaction проверяется тестом. Приёмка: попытка отправить секрет блокируется.
- **M26. Экспорт/импорт без credentials.** Перенос памяти между инстансами. Приёмка: импорт в чистый инстанс даёт те же ответы на фиксированном наборе.
- **M27. Soak памяти.** 72 часа с записью/чтением/консолидацией. Приёмка: нет утечки, размер стабилизируется, restore после SIGKILL корректен.
- **M28. Memory scorecard.** Один JSON+MD отчёт: integrity, retrieval, cost, continuity. Приёмка: отчёт генерируется одной командой и привязан к SHA.

## 4. Автономность: от планировщиков к доказуемому решению

### 4.1. Фактическое состояние

**Сильные стороны.** Есть полный набор «органов»: внутренние драйвы (`epistemic`, `novelty`, `competence`, `coherence`, `social`, `homeostatic`), генерация целей (`P67`, `B272`), экология и lifecycle целей (`P68`, `B273`), волевой арбитраж (`AgencyDeliberationEngine`), бюджет внимания (`CognitiveBudgetManager`), кворум (`CognitiveQuorumEngine`), исполнение проектов (`AutonomousProjectExecutor`), гейты (`B333`–`B336`), социальная инициатива (`AutonomousSocialInitiativeEngine`), самоулучшение (`LiveSelfImprovementSupervisor`) и bounded-журнал решений на 96 записей с объяснением.

**Слабые места.**

1. `AgencyDeliberationEngine` принимает решение формулой, а не моделью ценности: `override = 0.45 + intrinsic*0.4 − external*0.15`. Нет калибровки, нет сравнения с контрфактическим baseline, нет обучения этой политики.
2. 20+ движков в одном runtime. Часть из них — конкурирующие источники цели (P67, B272, SelfDirectedLife, LongHorizon, AutonomousProjectExecutor). Кто главный при конфликте — не доказано.
3. Decision receipt фиксирует выбор, но не доказывает, что выбранное действие действительно исполнено и что последствие привязано к тому же `decisionId`. Issue #865 — прямое свидетельство разрыва.
4. «Автономность» часто равна «scheduler tick». Нет обязательного контракта: внутренний сигнал → цель → оценка → план → разрешённое действие → независимый postcondition → receipt → обучение.
5. Инициатива может стать спамом: consent/quiet-hours описаны (#1181, #1182), но сквозной soak по false-positive инициативам не проведён.
6. Остановка не гарантирована на каждом этапе: cancellation, expiry stale intent, drain in-flight — реализованы частями.
7. Внешние side effects и ACK-loss: outbox #1182 ещё Draft; exactly-once не заявлен и не должен заявляться.

### 4.2. План по автономности (A1–A28)

**Волна A-A. Единый decision spine (P0)**

- **A1. Назначить одного владельца выбора действия.** `DecisionActionPipeline` + `AgencyDeliberationEngine`; остальные движки поставляют кандидатов, но не выбирают. Приёмка: в коде ровно один вызов, порождающий финальный `decisionId`.
- **A2. Контракт `DecisionRecordV2`.** Поля: tick, source (external/endogenous), drive contributions, goalId+origin, список кандидатов с фичами, выбранное действие, confidence, cost, risk, safety-вердикт, `decisionId`. Приёмка: схема валидируется на restore, неизвестные поля отклоняются.
- **A3. Убрать формулу арбитража.** Заменить эвристику на явную функцию полезности с весами из политики: ценность цели, ожидаемый исход, стоимость ресурса, риск, соответствие идентичности, давление среды. Приёмка: веса конфигурируемы и попадают в receipt.
- **A4. Калибровка уверенности.** Сравнивать заявленный `confidence` с фактическим success rate по бин-ам. Приёмка: ECE (expected calibration error) измерен и отслеживается.
- **A5. Контрфактический baseline.** Для каждого решения считать «что было бы при внешнем запросе как единственном сигнале». Приёмка: `counterfactual` в receipt — вычисляемый, а не шаблонный текст.
- **A6. Замкнуть `decisionId` → исполнение → исход.** Один идентификатор проносится через ActionGateway, receipt, observation, outcome и temporal credit. Приёмка: issue #865 закрыт регрессией «pending decision разрешается ровно один раз после restore/replay».
- **A7. Bounded pending-ledger.** Незавершённые решения истекают (например, 24 ч), не воскресают после рестарта, не дают кредит дважды. Приёмка: replay не создаёт второй кредит.
- **A8. Decision receipt completeness.** 100% решений имеют receipt; 100% исполненных — исход; 100% исходов — ссылку на witness. Приёмка: диагностика показывает дыры, а не средние.

**Волна A-B. Мотивация и цели (P0/P1)**

- **A9. Разделить три источника цели.** Пользовательский запрос, принятое обязательство, внутренний кандидат. Приёмка: inferred user intent не создаёт обязательство.
- **A10. Один lifecycle цели.** `proposed → active → blocked → done/failed/expired/superseded`, с причиной перехода. Приёмка: нет цели в двух состояниях одновременно.
- **A11. Приоритет и конфликт.** Явная функция приоритета: срочность, ценность, стоимость, зависимость, риск. Приёмка: конфликт целей разрешается детерминированно и объяснимо.
- **A12. Внутренние драйвы как измеримые сигналы.** Каждый драйв имеет источник, единицу, насыщение и вклад в решение. Приёмка: отключение драйва меняет выбор предсказуемо (ablation).
- **A13. Гомеостазис как veto.** Усталость/ресурс/тепло/батарея могут запретить действие, но не могут его инициировать в обход политики. Приёмка: при низком ресурсе дорогие действия блокируются.
- **A14. Бюджет внимания.** Концентрация не крадёт бюджет других подсистем. Приёмка: сумма бюджетов не превышает лимит; тест на «кражу».
- **A15. Стоимость до действия.** Каждый кандидат имеет оценку latency/RAM/денег/риска. Приёмка: действие с превышением лимита не диспатчится.
- **A16. Expiry и supersession.** Просроченная цель не исполняется; новая отменяет старую явно. Приёмка: stale intent не даёт side effect.

**Волна A-C. Безопасные действия и восстановление (P0)**

- **A17. Permission/risk/cost classification до dispatch.** Явная матрица: read-only, локальная запись, внешний side effect, необратимое. Приёмка: необратимое требует отдельного разрешения.
- **A18. Consequence analysis.** Для необратимых действий — прямые, вторичные, отложенные последствия и затронутые стороны. Приёмка: без анализа действие не проходит gate.
- **A19. One-shot approvals и разделение ролей.** Кто предлагает, кто одобряет, кто исполняет — разные субъекты. Приёмка: self-approval невозможен.
- **A20. Cancellation на каждом этапе.** До dispatch, во время, после отправки, до ACK. Приёмка: отмена не оставляет «полу-исполненного» состояния.
- **A21. ACK-loss → reconciliation, не retry.** При неоднозначности — read-only проверка провайдера; повтор только после `confirmed-not-delivered`. Приёмка: #1182-контракт, тест «crash после отправки не дублирует сообщение».
- **A22. Undo-first.** Для обратимых действий — компенсация и проверка возврата состояния. Приёмка: откат восстанавливает предыдущее состояние и не создаёт второй side effect.
- **A23. Social initiative boundaries.** Consent, quiet hours, анти-спам, частота, явная причина инициативы. Приёмка: soak классифицирует каждую инициативу как relevant/spam; false-positive rate измерен.
- **A24. Crash-safe continuity.** Довести #1174 (crash-safe journal + RecoveryWatchdog) до канона. Приёмка: SIGKILL в середине цикла → рестарт → незавершённое либо восстановлено, либо безопасно закрыто.
- **A25. Checkpoint parity.** #1170 (five-owner checkpoint envelope): все пять владельцев сохраняются и восстанавливаются согласованно. Приёмка: рассинхронизация ловится тестом.

**Волна A-D. Доказательство автономии (P1)**

- **A26. Критерий автономного цикла.** Автотест: внутренний сигнал → цель → план → gate → действие → postcondition → receipt → обучение. Приёмка: цепочка воспроизводится на 100 последовательных циклах без внешних подсказок.
- **A27. Soak автономии.** 72 часа: число инициатив, relevance, завершённость, отмены, ошибки, ресурс. Приёмка: отчёт с классификацией каждого случая.
- **A28. Autonomy scorecard.** Initiative precision, goal completion, override rate, unauthorized actions = 0, duplicate side effects = 0, receipt completeness = 100%, reconciliation success. Приёмка: один отчёт на SHA.

### 4.3. Что считается «автономностью» (зафиксировать в репозитории)

> Не tick и не количество модулей, а воспроизводимая цепочка: **внутренний сигнал → сформированная цель → оценка политики → план → разрешённое действие → независимый postcondition → receipt → обучение/рефлексия**. Всё, что не проходит эту цепочку, — планировщик, а не автономия.

## 5. Саморазвитие: от лаборатории к управляемому контуру

### 5.1. Фактическое состояние

**Сильные стороны.** `P36AutonomousSelfDevelopment` — не заглушка: он выбирает область развития, считает ожидаемый прирост и стоимость, решает «инвестировать/восстановиться/наблюдать», открывает цикл, формирует campaign plan, принимает внешние свидетельства только от независимого evaluator, считает paired CI и требует holdout. `P23LearningEngine` содержит population search, Pareto-архив, независимого оценщика, подписанные shadow-свидетельства, versioned candidate store, approval-request CLI и rollback. После #1157 авторство возникает только по подтверждённому исполнению, а не по выбору.

**Слабые места (из карты 24.11 и кода):**

1. **`TheInventionLoop` не подключён** к Core/Agency: протокол независимой научной проверки существует, но не связан с promotion P23 или с self-repair.
2. **`P53DevelopmentalSelfModificationLab` не создаётся** в проверенных entrypoints. Более того, его `test()` считает shadow и holdout из одного набора входов, а `periodic()` может сам продвинуть кандидата по счётчику. Это не production-policy writer; #1180 добавляет fail-closed и карантин v2→v3, но не делает P53 готовым к автономии.
3. **`SourceGraph`/`SelfModificationGuard` отсутствуют** в текущем дереве. Значит, структурной защиты «нельзя править evaluator/holdout/approval/identity» перед реальным source rewrite нет.
4. **Нет одного lifecycle кандидата.** Есть классы и workflow по отдельности; цепочка candidate → validation → independent holdout → signed admission → apply → postcondition → rollback не доказана end-to-end.
5. **Learning journal wiring** (ветка `aspect/learning-journal-wiring-port-20261123`) не имеет открытого PR — работа не в каноне.
6. **Свежесть свидетельств** только что введена в Draft #1177: без неё старый подписанный shadow-receipt мог авторизовать промоушен.
7. **Метрики саморазвития смешаны с proxy.** Нет отдельного scorecard: сколько изменений реально улучшили downstream-поведение, сколько откатили, каков regression rate.

### 5.2. План по саморазвитию (S1–S30)

**Волна S-A. Фундамент: авторство, свидетельства, запретные зоны (P0)**

- **S1. Зафиксировать инвариант авторства.** Намерение ≠ авторство; авторство ≠ исполнение; исполнение ≠ подтверждённый результат. Приёмка: pending-ledger, кредит только по verified outcome (#1157), регрессия на spoofed boolean.
- **S2. Довести #1153 в канон.** P0-фиксы MemoryOS2 + self-authorship. Приёмка: exact-head CI, TDD red-gate, restore round-trip.
- **S3. Довести #1177.** Свежесть shadow-evidence: `record`, `promotion`, `persisted-active`. Приёмка: stale record/promotion отклоняются, активный скилл остаётся проверяемым, будущие метки времени отклоняются.
- **S4. Запретные зоны изменений.** Явный список: evaluator, holdout-датасеты, approval keys, identity anchors, trust roots, CI-workflow, migration chain. Приёмка: попытка изменения блокируется на уровне gate, а не ревью.
- **S5. `SourceGraph` (узкая интеграция).** Не тащить старый Draft #698 целиком: построить граф импортов и обратного влияния на текущем SHA. Приёмка: граф генерируется одной командой, детектит циклы и достижимость запретных зон.
- **S6. `SelfModificationGuard`.** Правило: изменение файла из запретной зоны или его транзитивного зависимости требует host-owned receipt. Приёмка: тест «патч в evaluator без receipt отклонён».
- **S7. Patch admission contract.** База SHA, список файлов и диапазонов, digest, автор, ревьюер, независимые paired outcomes, план отката. Приёмка: без любого поля — отказ.

**Волна S-B. Один lifecycle кандидата (P0/P1)**

- **S8. Единый `ImprovementCandidate`.** Типы: parameter, policy, skill, model adapter, architecture. У каждого — свой уровень допуска. Приёмка: нельзя повысить тип изменения без соответствующего разрешения.
- **S9. Разделение сплитов.** Train / validation / calibration / holdout физически раздельны; генератор не видит holdout. Приёмка: leakage-тест на пересечение групп.
- **S10. Пять paired seeds.** Минимум для confirmatory-заявки; exploratory и confirmatory — разные отчёты. Приёмка: один seed не даёт права на промоушен.
- **S11. Метрики кандидата.** Primary: downstream task success. Secondary: transfer, forgetting, calibration, regression rate, latency, RAM, стоимость. Приёмка: заранее объявленный MDE и допустимая регрессия.
- **S12. Negative control.** Кандидат-пустышка проходит тот же путь и должен быть отвергнут. Приёмка: контроль не промоутится ни при каких условиях.
- **S13. Signed admission.** Промоушен — только по подписанному артефакту от host-owned ключа, привязанному к точному payload и версии. Приёмка: копия полей без подписи не принимается.
- **S14. Apply + postcondition.** После применения — независимая проверка результата, а не отчёт самого кандидата. Приёмка: действие без postcondition считается незавершённым.
- **S15. Rollback.** Автоматический откат при деградации primary или нарушении инварианта. Приёмка: тест «ухудшение target score → откат → восстановление baseline».
- **S16. Один trace.** `candidateId → proposalId → approvalId → applyReceipt → outcomeId` в одном журнале. Приёмка: любой промоушен трассируется до решения, которое его инициировало.

**Волна S-C. Метакогниция и self-repair (P1)**

- **S17. `MetacognitiveEpisode` v1 (issue #613).** Один эпизод на полный цикл, а не на подшаг: прогноз, убеждение, выбранное действие, ожидаемый/наблюдаемый исход, ошибка, противоречие, рефлексия, accept/reject/rollback. Приёмка: эпизод воспроизводим после рестарта.
- **S18. Калибровка.** Confidence из эпизода сверяется с фактическим исходом по бин-ам. Приёмка: ECE и reliability-диаграмма в отчёте.
- **S19. Противоречие не перезаписывает факт.** Спорное свидетельство создаёт dispute/hypothesis. Приёмка: подтверждённый факт и явная коррекция пользователя не затираются.
- **S20. Рефлексия → только governed path.** Никакой self-authored policy не активируется без approval/holdout/rollback. Приёмка: обходной путь отсутствует в call graph.
- **S21. Подключить `TheInventionLoop`.** Один вход: гипотеза self-repair → протокол → независимый проверяющий → репликация → решение. Приёмка: acceptance InventionLoop виден в promotion-receipt.
- **S22. P53 — только изолированный эксперимент.** До появления раздельных preregistered holdout и host-authorized receipt не давать ему права писать policy. Приёмка: P53 не входит в production-path (статический аудит).
- **S23. Метакогнитивная диагностика.** Lineage эпизодов и калибровка без раскрытия приватного контента. Приёмка: отчёт по эпизодам без raw-текста.

**Волна S-D. Пластичность по уровням допуска (P1/P2)**

- **S24. Behavioral plasticity.** Ограниченные скалярные параметры (веса драйвов, пороги) — быстрый цикл, откат обязателен. Приёмка: изменение в пределах bounds, иначе отказ.
- **S25. Skill adaptation.** Новые процедуры — только через candidate lifecycle с holdout. Приёмка: скилл не активен до подписи.
- **S26. Model adapter.** LoRA/QLoRA-артефакты — реестр, base-model fallback, проверка происхождения. Приёмка: адаптер без версии и hash не загружается.
- **S27. Architecture/morphogenesis.** Только внутренние microcircuits и только с отдельным разрешением; не редактирование файлов проекта. Приёмка: morphogenesis не меняет source tree.
- **S28. Долгосрочная непрерывность.** Restart, soak, stale intent, checkpoint parity, способность остановиться. Приёмка: 72-часовой прогон с журналом каждого изменения.

**Волна S-E. Доказательство пользы (P1)**

- **S29. Self-development scorecard.** Число кандидатов, доля дошедших до holdout, доля промоушенов, regression rate, rollback success, transfer delta, forgetting delta, ECE, стоимость. Приёмка: отчёт на SHA, без усреднения по несравнимым прогонам.
- **S30. Публичный статус.** Разделять `IMPLEMENTED / CONNECTED / TESTED / MEASURED / RELEASED`. Приёмка: ни один пункт не переходит в `MEASURED` без независимого отчёта.

### 5.3. Ключевое правило

> Саморазвитие — это **не** «система меняет себя». Это **система предлагает изменение, доказывает его независимо и умеет откатить**. Всё остальное — либо эксперимент, либо недопустимый риск.

## 6. Общий контур: как три аспекта замыкаются друг на друга

### 6.1. Единый сквозной контракт (C1–C12)

- **C1. Один `decisionId` на всё.** Память (recall), автономия (выбор), саморазвитие (изменение) ссылаются на один идентификатор. Приёмка: трассировка от записи в памяти до применённого изменения без разрывов.
- **C2. Один `outcomeId` на всё.** Любой исход имеет независимого witness и тип: observed / verified / inferred. Приёмка: `inferred` не даёт learning credit.
- **C3. Один журнал свидетельств.** `CognitiveEventFabric` + ActionGateway receipts + promotion receipts. Приёмка: нет второго журнала с теми же фактами.
- **C4. Один restore-порядок.** Все владельцы восстанавливаются в детерминированном порядке; проекции строятся после канона. Приёмка: restart parity тест на 5 владельцах (#1170).
- **C5. Один деградированный режим.** При недоступности LLM/embedding/верификатора система честно деградирует, а не выдумывает. Приёмка: отчёт «кто сгенерировал» и «почему отказано».
- **C6. Один privacy-периметр.** Секреты и приватные строки не попадают ни в embeddings, ни в логи, ни в receipts. Приёмка: redaction-тест на всех трёх аспектах.
- **C7. Один бюджет ресурсов.** Память, внимание, обучение и инициатива делят общий лимит. Приёмка: сумма не превышает лимит; «кража» бюджета блокируется.
- **C8. Один failure mode.** Ошибка, неопределённость и таймаут ведут к abort/quarantine/rollback, а не к оптимистичному продолжению. Приёмка: fault injection на каждом слое.
- **C9. Один scorecard.** Три блока в одном отчёте + сводный индекс. Приёмка: генерируется одной командой на SHA.
- **C10. Один Definition of Done.** `IMPLEMENTED → CONNECTED → TESTED → MEASURED → RELEASED`. Приёмка: статус нельзя перескочить.
- **C11. Один способ отката.** Любое изменение — reversible или явно помечено irreversible с отдельным разрешением. Приёмка: откат проверен на каждом уровне.
- **C12. Один запрет на самообман.** Никаких заявлений о сознании, субъектности, «улучшении recall» без независимого отчёта. Приёмка: аудит формулировок в документации.

### 6.2. Северная метрика проекта

```
Качество памяти  →  Качество решений  →  Подтверждённый прирост
   Recall/MRR         success/calibration      Δ primary + Δ retention
   false recall       override/receipts        без роста регрессий
```

Сводный индекс (`NK1_CognitiveReadinessIndex`) — **не среднее по модулям**, а три независимых гейта. Нельзя компенсировать слабую память хорошей автономией: каждый гейт проходной отдельно.

## 8. Критерий завершения

Три аспекта можно считать развитыми, когда одновременно верно:

1. **Память.** На независимом RU/EN holdout есть воспроизводимый отчёт: retrieval не хуже baseline, false recall не вырос, restore не теряет и не дублирует, `forget` не воскресает, стоимость на 10k записей известна.
2. **Автономность.** 100 последовательных циклов дают полную цепочку «внутренний сигнал → цель → план → разрешённое действие → независимый postcondition → receipt → обучение», без дублей side effects и с нулём несанкционированных действий.
3. **Саморазвитие.** Хотя бы одно изменение прошло полный путь candidate → 5 seeds → holdout → signed admission → apply → postcondition → rollback-тест, и его польза подтверждена downstream-метрикой, а не proxy-score.

Всё остальное — либо исследование, либо подготовка. И это нормально: проект силён именно тем, что уже умеет отличать одно от другого.
