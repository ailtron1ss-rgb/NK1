# WorkPass336 — сравнение, анализ и безопасный рост навыков

## WorkPass342 — ограничение диагностического контекста (2026-10-25)

- Регрессионный тест проверяет минимальный и чрезмерно большой лимит advisory-контекста, а также детерминизм при неизменной истории опыта.
- Диагностический путь ограничен максимумом 12 гипотез и 12 целей обучения. Этот лимит не меняет исходный план исправления и не влияет на правила независимой оценки и активации.

## WorkPass341 — передача гипотез опыта в генератор исправления навыка (2026-10-25)

- Генератор новой версии навыка теперь получает ограниченный advisory-контекст из гипотез размышления и ранжированных целей, вычисленных по сохранённым исходам NK1.
- Контекст не содержит исходные ID опыта, ключи контекста или ID задач. Он отмечен как advisory: не подтверждает качество кандидата, не расширяет список задач, которые следует исправить, и не заменяет независимую оценку.
- Проверка плана исправления по validation, безопасность, fingerprint точного payload, holdout-изоляция, provenance, shadow-доказательства и отдельное одобрение активации остаются обязательными.
- Регрессионный тест расширен: он записывает серию повторных неудачных действий в P23, проверяет получение соответствующей гипотезы генератором и проверяет отсутствие исходных ID в переданном контексте.

## WorkPass340 — проверка входа P23 до записи опыта (2026-10-25)

- Первый exact-head CI обнаружил только ошибку сужения nullable-типа `trace.selected`; явная локальная проверка добавлена, после неё обязателен повторный полный workflow.
- На входе `recordExperience` теперь проверяются структура trace, ID, когнитивный tick, timestamp, action, выбранная оценка, списки кандидатов/предсказаний и нормализованные потребности состояния. Повреждённые записи отклоняются до изменения состояния.
- Значения `success`, `surprise`, `predictedUtility` и `confidence` должны быть конечными и находиться в `0..1`. Они сохраняются без скрытого clipping; некорректное число не превращается в правдоподобную метку.
- Ошибка не помечает trace как обработанный: после исправления источника тот же ID может быть записан с валидным результатом. Это не подтверждает достоверность результата само по себе; независимые доказательства и promotion gate остаются обязательными.

## WorkPass339 — целостность доказательств для размышлений (2026-10-25)

- Результат WorkPass339: GitHub Actions run `40161068610` завершился `success` на exact HEAD `53f4bde72029d92b7b2cec91dc2de81e28cfd011`. Пройдены четыре regression suite, включая `WORKPASS339_REFLECTION_EVIDENCE_NORMALIZATION=PASS`, и TypeScript runtime check (`TYPECHECK=PASS mode=tsc compiler=PATH`).

- Входные записи размышления теперь проверяются до расчёта гипотез: нужны ограниченные строки идентичности, конечные оценки в диапазоне `0..1`, неотрицательный безопасный `tick` и корректная временная метка. Повреждённая запись не превращается молча в провал.
- Повторная доставка одной и той же записи с тем же ID и теми же данными считается один раз. Если один ID повторён с конфликтующими результатами, такой ID исключается из текущего расчёта полностью.
- При одинаковом когнитивном `tick` применяется стабильная сортировка по времени и ID. Поэтому «последние восемь наблюдений» не зависят от порядка поступления.
- Добавлен отдельный тест: дубли, конфликтующие IDs, `NaN`, `Infinity`, значения вне диапазона, ошибочные tick/time и перестановка одинаково-временных записей. Он подключён к WorkPass339 Node.js 24 workflow.
- Это улучшает качество материала для размышлений, но само по себе не подтверждает правильность гипотез: решения по навыкам всё ещё требуют независимой оценки и отдельного подтверждённого цикла активации.


## Дополнение WorkPass338 — сохранение доказательств успешного исправления

- План, переданный генератору навыка, сохраняется как исходный план ревизии. Его fingerprint и список измерений записываются в provenance созданного кандидата; последующая оценка больше не подменяет историю того, что именно генерировалось.
- Повторная независимая оценка выполняется для точного нового payload. Если она показывает ноль оставшихся целей оптимизации, кандидат всё равно можно поместить в staging при условии, что исходный план был непустым и проверка безопасности не выявила блокирующих проблем.
- Результат API различает `plan` (что просили исправить) и `postRevisionPlan` (что осталось после исправления). Это не разрешает автоматическую активацию: остаются отдельные ворота независимого сравнения, shadow evidence и явного подтверждения.
- Добавлен end-to-end regression с подлинными в рамках fixture подписанными результатами. Тест подтверждает прирост качества, отсутствие остаточных целей, сохранение исходного fingerprint и staging отдельной версии.
- Запуск CI и TypeScript-проверки пока нельзя считать успешными, пока не получен отчёт для точного HEAD.

## Дополнение WorkPass337 — происхождение экспериментальных данных

- Строгий анализ роста теперь не принимает отчёты без канонического манифеста, fingerprint validation/holdout-планов, разных method ID для baseline и candidate и корректного номера попытки.
- Для каждого запуска требуется planned run ID. Поддельно выглядящий набор отчётов без авторитетного плана отклоняется ещё до допуска к активации.
- Диагностические тесты могут явно использовать synthetic fixture, но production promotion не передаёт флаг отключения этой проверки.
- Добавлен тест, подтверждающий отказ в активации при полном по форме envelope без canonical experiment authority.

## Что изменено

1. **Сравнение на уровне независимых seed.** Компаратор сохраняет проверку совпадения задач, trial, seed, split, плана и среды, а затем вычисляет улучшение отдельно по каждому seed. Для каждого split возвращаются число парных seed, средняя дельта, 95%-й t-интервал, доля seed с улучшением, худшая дельта и полнота покрытия задач.
2. **Оценка роста — не только средняя оценка.** В каноническом пути активации требуется не менее пяти полностью парных seed в validation и holdout; улучшение минимум на 60% validation seed; нижняя граница 95%-го доверительного интервала выше нуля; одинаковый набор задач для каждого seed; отсутствие holdout-регрессии хуже -0,15 на отдельном seed. Сохраняются прежние требования к приросту validation, aggregate holdout, числу holdout-задач и нулевым нарушениям безопасности.
3. **Подтверждённые неудачи учитываются как отрицательные примеры.** Если независимый проверяющий подтвердил связь результата с конкретным запуском, неуспешный результат учитывается как нулевая успешность, а не удаляется как «недоверенный». Непривязанные трассы, отсутствующие run ID и результаты с нарушениями безопасности по-прежнему отклоняются.
4. **Закрыт обход сильной проверки.** Legacy-метод продвижения, принимавший только массивы отчётов без envelope с provenance, теперь fail-closed. Для активации нужен полный envelope независимого оценщика, привязка к shadow evidence и существующее аутентифицированное подтверждение.
5. **Регрессии и CI.** Добавлены сценарии устойчивого улучшения на пяти seed, единичного holdout-провала при положительной общей средней оценке, недостаточного числа seed и старого обходного пути. Новый Node.js 24 workflow предназначен для запуска целевых регрессий на точной ветке.

## Почему это важно

Система не должна считать, что «обучилась», лишь потому, что один запуск оказался удачным или средняя оценка улучшилась. Повторяемость по seed, независимая проверка, контроль отдельных регрессий и сохранение отрицательной обратной связи уменьшают риск случайного улучшения и подгонки.

## Ограничения и статус доказательств

- Это усиление **критерия допуска к активации**, а не доказательство общего прироста интеллекта или качества на реальных задачах.
- Доверительный интервал использует t-аппроксимацию на ограниченной выборке seed; это оценка неопределённости, а не универсальная гарантия.
- Реальный host/container sandbox, независимо управляемые verifier/scanner, долгий soak, полный TypeScript-аудит и тесты на устройстве/браузере остаются отдельными воротами.
- Код, регрессии и workflow добавлены в feature-ветку; пока нет успешного результата точного запуска Actions, проверки **не считаются пройденными**.
- `main`, публикационная линия и GitHub Release ZIP этим проходом не менялись. Ветка предназначена для ревью и не слита автоматически.
