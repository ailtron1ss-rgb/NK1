# WorkPass529 — отдельный проверенный маршрут зрелости P36

**Дата:** 24 октября 2026 г.  
**Рабочая ветка:** `feature/learning`  
**PR:** [#79 → integration](https://github.com/ailtron1ss-rgb/NK1/pull/79)  
**Проверка выполнения:** в этой сессии тесты/typecheck не запускались; результат CI для текущего HEAD нужно подтвердить отдельно.

## Что было неверно

В основном цикле Core P36 вызывал `observeDevelopmentalOutcome({ verified: verifiedNow, ... })`, где `verifiedNow` означал наличие внутреннего world transition или внешнего проектируемого сигнала. Это полезно для ряда обучающих контуров, но не является тем же доказательством, что неизменяемая квитанция независимого evaluator-а. После введения строгой проверки вызов не должен увеличивать зрелость; он лишь создавал бессмысленные отклонённые попытки каждый раз, когда обычный цикл сообщал reward.

## Изменения

- Удалён legacy-вызов P36 maturity из обычного feedback-цикла. Внутренний переход и reward по-прежнему доступны прочим обучающим системам, но больше не претендуют на независимую зрелость P36.
- Стандартизирован тип входа `kind: 'developmental-outcome'` в `developmentalOutcomeVerificationInput`. Этот маркер входит в нормализованный кортеж, который verifier должен проверить; его нельзя подменить другим типом события.
- `OrganismCore.finalizeToolOutcome` маршрутизирует reserved tool `organism.learning.p36.evaluate-evidence` в два разных пути:
  - обычная оценка baseline/treatment/holdout → `recordExternalEvidence`;
  - исход обучения с delayed/transfer → `observeDevelopmentalOutcome`.
- Оба пути требуют успешное выполнение инструмента, external-postcondition receipt, точные tool/execution/decision ID и существующий сохранённый selected trace. Обычный `verified: true` не проходит этот gate.
- Добавлен отдельный публичный Core-метод `p36RecordDevelopmentalOutcome`, повторно проверяющий те же ID и квитанцию. Повторная доставка уже применённого точного maturity receipt остаётся идемпотентной и не увеличивает счётчик отказов.
- Регрессионный интеграционный сценарий охватывает отказ для неподвязанной maturity-квитанции, принятие связанной квитанции, сохранение числа проверенных исходов и прямой повторный вызов Core-метода. P36 unit-test также проверяет, что точный replay не считается отказом.

## Текущие ограничения

- Зарезервированный маршрут — это контракт подключения. Этот проход не устанавливает реальный host-owned независимый evaluator в production; хост должен зарегистрировать его под зарезервированным ID. Тестовый evaluator остаётся fixture и не доказывает наличие production authority.
- Восстановление после перезапуска по-прежнему fail-closed: P36 не доверяет сериализованным счётчикам/весам без повторной аутентификации долговечного доказательства. Durable signed-proof re-ingestion остаётся открытой задачей.
- GitHub API на предыдущем точном HEAD возвращал ноль workflow/check runs; текущие WorkPass529 test/typecheck результаты не подтверждены. Никакого empiric learning uplift не заявляется.

## Критерий закрытия

P36 может выбирать направление развития и собирать гипотезы автономно, но не может повышать собственную зрелость на основании обычного reward или булева флага. Для maturity необходим отдельный evaluator result, связанный с конкретным успешным ActionGateway execution и сохранённым решением. Затем нужны точный CI, production authority configuration и независимый эксперимент с retention/transfer.

`main` и GitHub Release ZIP не изменялись.
