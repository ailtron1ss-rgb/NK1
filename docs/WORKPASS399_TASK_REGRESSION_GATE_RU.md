# WorkPass399 — отдельный барьер регрессий по validation-задачам

**Ветка:** `feature/learning`  
**Компонент:** SkillLearnBench-compatible P23 candidate gate  
**Статус:** механизм, параметры и регрессия закоммичены; фактическое выполнение теста ожидает runner с доступными логами.

## Почему это изменение нужно

Средний прирост на validation-наборе может скрывать большой провал на одной задаче, если прирост на других задачах его компенсирует. У NK1 уже были отдельные ограничения для macro-average, минимального числа различных validation-задач, общего holdout и регрессий семейств holdout-задач. Не хватало самостоятельного ограничения для каждой paired validation-задачи.

## Что сделано

- Добавлен параметр `maximumValidationTaskRegression01`, по умолчанию `0.20`. Значение ограничено диапазоном [0, 1]; нечисловое или выходящее за пределы значение отклоняется.
- Для каждой задачи сначала усредняются её сопоставленные trial-оценки baseline и candidate, затем считается разница. Повторные прогоны одного task ID не превращаются в дополнительные голоса.
- Если хотя бы одна задача падает больше разрешённого порога, gate выдаёт `validation-task-regression-exceeds-tolerance`; отчёт возвращает число таких задач в `validationTaskRegressions`.
- Добавлен сценарий, в котором общий validation score растёт за счёт двух задач, но третья ухудшается выше порога. Новый gate блокирует кандидата, несмотря на положительный общий прирост.
- Проверяется и неверная конфигурация нового параметра. P26 Learning Validation уже включает файл теста `p29-hermes-reflective-candidate-gate.mjs` и path filter для адаптера.

## Исследовательская основа

Механизм соответствует трёхуровневой оценке SkillLearnBench (качество навыка, траектория, исход задачи) и учитывает эмпирическую проблему continual skill learning: методы могут выигрывать на одних задачах и терять на других; саморефлексия без независимой обратной связи может приводить к дрейфу. Новый барьер — дополнительная политика NK1, а не утверждение о наличии в первоисточнике именно такого порога.

- Hermes Agent Self-Evolution: https://github.com/NousResearch/hermes-agent-self-evolution
- Reflexion: https://arxiv.org/abs/2303.11366

## Ограничения и следующие шаги

Порог 0.20 — инженерный safety default, а не научно оптимальная константа; его следует оценивать на multi-seed task suite. Этот guard снижает риск локального регресса, но не заменяет holdout, проверку safety, независимый evaluator, доверенное approval и rollback test. В текущем проходе не заявляется статистически подтверждённое улучшение обучения: GitHub Actions пока не предоставляет runner step logs.
