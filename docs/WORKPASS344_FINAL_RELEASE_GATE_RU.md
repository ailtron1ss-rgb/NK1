## Defects found

1. `npm run release:verify` omitted the canonical `verify-release-metadata.mjs` gate. A green final tree could coexist with root/SUPER_VERSION, app/runtime manifest/lockfile, current-status inventory or score metadata drift.
2. The first integration run after adding the metadata gate exposed a false positive: architecture scanner interpreted a test string literal as an extra import edge.
3. After fixing that false positive, the integration run completed research smoke but the final audit found Python `__pycache__/*.pyc` generated by the very tests just executed. The strict release check was correctly failing the workspace, but the CI ordering needed an explicit transient-cache policy.
4. The verifier summary reported `failed: 0` because UI/architecture/metadata subprocesses passed even though tree-hygiene errors made overall `ok=false`. The summary now separates `directCheckFailures` and `treeFailures`, and `failed` includes both.

## Implementation

- `verify-final-release.mjs` accepts `--root`, rejects unknown args and runs UI wiring, architecture and release metadata as mandatory gates.
- Default `npm run release:verify` remains strict about generated Python caches.
- New `npm run release:verify:ci` is used only after Research Bridge smoke. It permits only a `.pyc` file inside an `__pycache__` path and lists the ignored file in warnings. It does **not** ignore other file types in cache directories or bytecode outside them.
- Root `test:final-release-verifier` and `audit:workpass70` are wired to the strict gate. Unified integration workflow runs the focused regression then `release:verify:ci`.
- Seven test scenarios cover metadata pass/fail/missing validator, unknown CLI argument, strict rejection of generated bytecode, explicit CI-only allowance, and attempts to hide stray/non-bytecode artifacts under the override.
- The substrate wiring regression's expected import assertion is constructed from tokens to avoid the architecture scanner's false positive.
