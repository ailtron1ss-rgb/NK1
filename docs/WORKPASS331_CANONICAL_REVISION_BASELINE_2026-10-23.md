# WorkPass331 — bind P23 revision fitness to canonical active/source payloads

**Date:** 23 October 2026  
**Branch:** `workpass328-upstream-donor-gate`, based on `workpass70-source`  
**Purpose:** close a trust gap in the reflective skill revision loop: the repair provider previously supplied `baseline` and `candidateEvaluation` reports that influenced the revision plan and the final baseline-vs-new-candidate gate, even though only the *generated* candidate was freshly evaluated through the configured independent evaluator.  
**Evidence status:** source, tests and CI wiring are committed; exact-head execution/typecheck is unverified because current GitHub Actions jobs stop before running steps.

## 1. Failure mode

The canonical `P23CompoundRepairRevisionCoordinator` snapshots whatever `baseline` and `candidateEvaluation` data its input provider returns. `P23LearningEngine.generateAndStageReflectiveSkillRevision()` uses those reports to derive repair targets and later compares the fresh generated candidate against the supplied baseline.

Before this pass, `withIndependentCandidateEvaluation()` replaced the evaluator used after generation but copied the provider's baseline/source reports unchanged. A provider that was incorrect, stale, or compromised could supply a low baseline and steer the promotion comparison without falsifying the generated candidate's independently measured output. Merely structured-cloning these reports protected them against later mutation, but did not establish where they came from.

## 2. What changed

### Canonical source of both comparison payloads

In production, `OrganismRuntime` now supplies a resolver which reads the current active version and the requested source candidate from `P23LearningEngine.verifiedSkillCandidateSnapshot()`, the existing authenticated/versioned skill store. It rejects a missing active baseline, a missing/mismatched/rolled-back source candidate, or malformed payload fingerprints. The provider's own payload fields are never used to select the baseline or source candidate.

The resolver includes an `assertStillCurrent` check. After the baseline/source runs and again after the new candidate's independent evaluation, the runtime re-reads the canonical store and fails if the active version or source-candidate version/fingerprint changed during the cycle. This reduces the risk of applying fitness measured against a stale active version.

### Three independently named evaluation methods, one immutable task design

The host evaluator configuration now supplies three different manifest-declared method names:

- `baselineMethod`: re-evaluate the active skill payload;
- `sourceCandidateMethod`: re-evaluate the canonical source candidate;
- `experimentAuthority.method`: evaluate the newly generated revision candidate.

All three methods must exist in both the fixed validation and holdout plans and must be distinct. The plans, manifest, environment fingerprint, task IDs, trial IDs, seeds and split boundaries must match across evaluations. The same host-owned executor/verifier/safety-scanner authorities run each exact payload.

The provider's original report arrays and its own evaluator function are ignored on the canonical path. The P23 engine receives report arrays generated by the independent evaluator itself. The freshly generated candidate is also checked against both active-baseline and source-candidate evaluation envelopes before the result is returned to P23.

### Matching is strict without erasing real failures

The new envelope check validates payload/evaluation digests, environment and task-plan fingerprints, manifest/validation-plan/holdout-plan identities, distinct method identities, attempt identity, and one-to-one task/trial/seed/split bindings. It does **not** turn a failing execution into a passing outcome: failed postconditions and safety findings remain in the actual evaluation reports. An evaluator record may truthfully represent a failed or unbound execution; such a row is never converted into verified success. Existing P23 safety/fitness gates still decide whether the generated revision can be staged.

The production path fails closed when the canonical source resolver or the three method declarations are absent. Development mode keeps a documented compatibility path for older provider fixtures, but that fallback does not satisfy the production gate.

## 3. Regression coverage

Added `runtime/neuro-kurisu/tests/workpass331-canonical-revision-baseline.mjs`. It constructs a fixed four-task validation/holdout manifest across two seeds and verifies:

1. malicious provider-supplied baseline/candidate report identities are ignored;
2. active/source payloads are evaluated by the independent evaluator under separate manifest-declared methods;
3. a real source-candidate failure is kept as a failure rather than falsely promoted to a verified pass;
4. the new candidate is independently evaluated using the same task identities and plans;
5. provider-supplied evaluator code is never invoked;
6. changed active/source store identity causes the revised evaluation to fail instead of using stale comparison data;
7. production construction fails when no canonical-source resolver is provided.

The test is registered as `test:workpass331:canonical-revision-baseline`, included in root `audit:quick`, and added as a named WorkPass71 core CI step.
