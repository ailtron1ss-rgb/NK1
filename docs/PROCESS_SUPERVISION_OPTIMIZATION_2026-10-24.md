# NK1 — оптимизация внешних процессов и запуска сервисов

**Дата:** 24 октября 2026  
**Ветка:** `optimization/process-supervision-20261024`  
**Статус:** код и регрессионные проверки добавлены; точный GitHub Actions run и полная интеграционная проверка должны подтвердить результат.

## Что изменено

### Управляемый запуск процессов

`tools/process-supervisor.mjs` стал общей точкой для запуска одноразовых команд и остановки долгоживущих процессов.

- Для команд задан ограниченный срок выполнения, контролируемое завершение и эскалация до принудительного завершения.
- stdout и stderr ограничены по объёму; сохраняется их последний фрагмент, полезный для диагностики, вместо неограниченного накопления в памяти.
- На POSIX дочерние процессы запускаются в отдельной группе, чтобы остановка npm/Node/Python-сервиса могла очистить созданные им дочерние процессы.
- HTTP readiness-проверка ожидает фактический успешный ответ с ограничением времени на запрос и общий дедлайн.

### Интеграционная проверка

В `tools/verify-integration.mjs` заменено фиксированное ожидание 3,5 секунды на опрос готовности Runtime и Research Bridge. Каждый HTTP-запрос теперь имеет тайм-аут, проверки TypeScript ограничены 180 секундами, а вывод команд сохраняется в ограниченном диагностическом хвосте.

Каждый запуск использует уникальную папку внутри `.verify-state`. Параллельные прогоны больше не удаляют общее состояние друг друга при старте. Временное состояние удаляется после остановки запущенных сервисов.

### Development и production launcher

`tools/super-dev.mjs` и `tools/super-start.mjs` используют общий supervisor: ошибка запуска явно регистрируется; неожиданное завершение обязательного сервиса останавливает весь запуск с ненулевым кодом; shutdown сначала завершает процессы и их доступную группу, а затем завершает родительский launcher. Это исправляет прежний риск, когда production launcher мог выйти с кодом успеха после аварийного завершения сервиса.

### Регрессии и CI

`tools/process-supervisor.test.mjs` покрывает код завершения и поток вывода, ограничение объёма логов, ошибку отсутствующего executable, timeout/kill escalation и ожидание HTTP readiness. Root-скрипт `test:integration` запускает этот набор перед интеграционной проверкой. Добавлен отдельный Node 24 workflow, который проверяет supervisor при изменениях связанных файлов.

## Как проверить

```bash
npm run test:process-supervisor
npm run test:integration
```

Первую команду можно запускать отдельно: тесты не требуют установки зависимостей приложения. Вторая запускает полную проверку сервиса и TypeScript.

## Критерии и ограничения

- Не заявляется ускорение когнитивных циклов, памяти или обучения: это оптимизация управления разработческими, тестовыми и runtime-процессами.
- Экономия времени запуска не заявляется до измерения на том же commit и окружении: readiness теперь может завершиться раньше фиксированной задержки, но будет ждать дольше, если сервис реально стартует медленнее.
- Нужен успешный запуск focused workflow на точном HEAD и прогон `npm run test:integration` на машине с установленными app/runtime зависимостями.
- Windows использует доступный прямой сигнал процессу; POSIX дополнительно поддерживает остановку отдельной группы процессов. Полноценный Windows process-tree kill пока не добавлен.
- Эта ветка не меняет `main` и не публикует новый Release ZIP.

## Второй проход — общая точка запуска для вспомогательных процессов

- `tools/super-install.mjs` теперь использует тот же supervisor для `npm ci`, сохраняя живой вывод npm, но ограничивая объём диагностического буфера и переиспользуя общий timeout/process-group cleanup. Удалён второй независимый механизм завершения процессов.
- `tools/super-doctor.mjs` запускает независимые Node/npm version probes параллельно, каждый с 5-секундным дедлайном и небольшим пределом вывода. Удалён ранее вычислявшийся, но нигде не использовавшийся subprocess `python3 --version`.
- `tools/verify-final-release.mjs` выполняет два независимых read-only аудита параллельно, ограничивает время и размер их вывода и сканирует файловую метаинформацию партиями по 64 файла. Так устраняются последовательные ожидания и бесконтрольное число одновременно выполняемых файловых операций.
- Focused Node 24 workflow дополнен синтаксической проверкой этих launcher/audit scripts и smoke-запуском `npm run doctor`.
- Добавлена регрессия, которая проверяет, что live streaming и ограниченное сохранение хвоста журналов работают одновременно.

Эти изменения уменьшают дублирование управления процессами и потенциальное время вспомогательных проверок. Фактическая скорость полного `release:verify` и `install:all` ещё должна быть измерена на одинаковом окружении; никаких числовых ускорений не заявляется.

### Миграции с контролируемым дедлайном

- `tools/super-migrate.mjs` переведён на общий supervisor, сохраняя строгий порядок: сначала optional app/DB migration при наличии `DATABASE_URL`, затем runtime persistence migration.
- Каждое действие получает дедлайн `NK_MIGRATION_TIMEOUT_MS` (по умолчанию 30 минут, допустимо 1–60 минут), ограниченный диагностический хвост и live streaming логов; timeout очищает доступную группу процессов и завершается ошибкой.
- Принудительная отмена миграции может оставить состояние, требующее проверки, поэтому в сообщении об ошибке явно указано не повторять миграцию вслепую: сначала проверить транзакционное/частично применённое состояние.
- Добавлен тест, гарантирующий, что некорректное значение тайм-аута отклоняется до запуска миграционных скриптов.
- В focused Node 24 workflow включены новый миграционный guard и регрессии установщика. Предыдущий CI обнаружил недостающий supervisor в временном installer-fixture; фикстура и структурированный timeout-диагностический контракт исправлены.
