## Проблема

В `VerifiedSkillPromotion` оценка по семействам уже присутствовала и блокировала выраженную отрицательную регрессию. Но общая статистически значимая прибавка могла пройти, даже если полезный для конкретного навыка класс задач оставался без улучшения. Это особенно важно при нулевых приростах tool-use/transfer: общий показатель способен скрыть профильную слабость.

При этом глобальный запрет на отсутствие прироста во всех семьях был бы неверным: специализированному memory-навыку не обязательно улучшать нерелевантные способы действия. Поэтому выбран явный, привязанный к назначению навыка контракт.

## Реализация

Добавлена настройка:

```ts
minimumFamilyGainByFamily?: Record<string, number>
```

Пример политики для общего агента, который обязан улучшить tool-use и transfer:

```ts
{
  minPairedTasks: 8,
  minCompleteSeeds: 3,
  minimumFamilyGainByFamily: {
    "tool-use": 0.05,
    "transfer": 0.05
  }
}
```

Порог — абсолютный прирост pass rate по семейству в диапазоне [0, 1]. Для каждого указанного семейства proposal должен содержать минимум `minCompleteSeeds` полных paired seeds и достигать заданного прироста. Если семейство не измерялось или coverage недостаточен, причина — `required-family-evidence-insufficient:<family>`; если прирост не достигнут — `required-family-gain-below-threshold:<family>`. В обоих случаях `gate.accepted=false`.

Если политика не указана, дополнительное требование к положительному приросту отдельных семей не навязывается; прежняя защита от крупных семейных регрессий сохраняется.

## Защита proposal и одобрения

Нормализованная evaluation policy хранится внутри proposal и входит в digest, из которого получается `proposalId`. Она включает минимум paired-задач, общий порог gain, допустимую семейную регрессию, minimum complete seeds и карту обязательных семейных приростов. Поэтому разные пороги приводят к разным proposal ID даже тогда, когда кандидат проходит обе версии политики. Изменение любого поля proposal после его создания по-прежнему нарушает проверку аутентичности.

Предложение не активирует навык автоматически: `canActivateAutomatically: false`, authenticated approval, shadow evidence и rollback путь остаются обязательными.

## Регрессии

В `tests/p23-verified-skill-promotion-proposal.mjs` на подписанном детерминированном fixture проверяется:

- общий прирост не скрывает нулевой прирост обязательного memory-семейства;
- tool-use допускается, когда измеренный прирост превышает обязательный floor;
- обязательный, но не измеренный transfer проваливается безопасным образом;
- неверный объект порогов и значения выше 1 отклоняются;
- две разные, но обе проходящие политики всё равно создают разные proposal IDs.

Тест и исходник уже находятся в существующих WorkPass110 path filters/шаге CI. Новые зависимости не добавлялись.
