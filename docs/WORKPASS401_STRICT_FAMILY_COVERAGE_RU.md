# WorkPass401 — строгая проверка наличия семейств задач

## Какая лазейка осталась

После WorkPass400 семейный регресс блокируется только когда отчёт содержит `taskFamily`. Это намеренно лучше, чем угадывать семейство по `taskId`, однако по умолчанию старые сценарии без семейной разметки могли получить `validationFamiliesEvaluated = 0` и всё ещё пройти остальные gate-проверки. Для production-эксперимента это может означать, что ожидаемая проверка доменного переноса фактически не выполнялась.

## Изменение

Добавлены два независимых параметра строгого режима:

- `minimumValidationFamilies` — минимум validation-семейств с достаточным числом различных задач.
- `minimumHoldoutFamilies` — минимум holdout-семейств с достаточным числом различных задач.

Оба параметра по умолчанию равны 0 ради совместимости с текущими legacy-тестами и отчётами. Экспериментальный профиль может установить 1 или больше и тогда не пройдёт promotion, если в соответствующем split нет требуемого количества семейств. Семейство засчитывается только если в нём есть минимум задач, заданный параметрами `minimumValidationFamilyTasks` или `minimumHoldoutFamilyTasks`.

Новые причины отказа:

- `validation-family-coverage-insufficient`
- `holdout-family-coverage-insufficient`

Неположительные, дробные или небезопасно большие значения отвергаются; параметры не приводятся к допустимым значениям автоматически. Для строгого режима caller обязан передать канонические метки; код не синтезирует их из имени задачи.

## Проверка регрессии

P29 добавляет сценарий, где validation и holdout имеют достаточные по старой схеме task-оценки, но не содержат меток семейств. При `minimumValidationFamilies: 1` и `minimumHoldoutFamilies: 1` отчёт фиксирует нулевую семейную coverage, получает обе причины отказа и остаётся ineligible. Отдельные тесты проверяют отрицательный validation минимум и дробный holdout минимум. Обычные тесты без family labels сохраняют старое поведение, когда строгие минимумы не заданы.

## Рекомендация настройки

Для benchmark/production evaluation использовать canonical manifest и включать строгое требование покрытия в profile, который управляет promotion. Не делать эти поля обязательными для всех исторических данных, иначе совместимость будет потеряна без возможности восстановить достоверные метки постфактум.

Дальнейшая задача — закрепить профиль эксперимента рядом с manifest/version/seed, чтобы выбор строгого режима был частью проверяемого плана, а не неявной настройкой вызывающего кода.
