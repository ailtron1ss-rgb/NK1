# NK1 — реестр интеграций из открытых проектов и исследований

**Дата:** 3 ноября 2026
**Назначение:** для каждого внешнего кандидата зафиксировать источник, лицензию, механизм, границу интеграции, ожидаемую пользу, риск, тест и решение. Реестр существует, чтобы не вендорить вслепую и не повторять тупики.

> **Правило допуска.** Внешний код не попадает в канонические владельцы напрямую. Сначала — изолированный адаптер, затем абляция против того же baseline и корпуса. Решение `ADOPT` означает «берём код или архитектуру»; `ADAPT` — «берём идею, реализуем сами»; `EVALUATE` — «нужен измеренный прогон»; `REJECT` — «не берём, причина записана».

> **Статус лицензий** указан по состоянию на дату реестра и должен перепроверяться перед вендорингом. Независимая проверка требуется для всего, что попадает в `ADOPT`.

---

## 1. Что именно требуется от интеграций

По приоритету проекта:

| Потребность NK1 | Чего не хватает сейчас | Кандидаты |
|---|---|---|
| Самоулучшение с реальной проверкой | `SandboxedSelfRewriteEngine.ts` — 4 строки; нет пула кандидатов, нет отбора | OpenEvolve, OpenAlpha_Evolve, AIDE² |
| Анализ кода | был только regex-граф; нет CST | tree-sitter |
| Память и время | `temporalLinks` есть, би-темпоральных окон валидности нет | Graphiti |
| Понимание опасности | статический анализ обработчиков действий | Semgrep, CodeQL |
| Ускорение самообучения | нет curriculum-отбора по переносу | RE-Bench, AIDE² |
| Локальный вывод | нет локального инференса | llama.cpp, Ollama |
| Голос | нет локального TTS/VAD | Piper, Silero VAD |

## 2. Память и знания

### C1. Graphiti (`getzep/graphiti`) — Apache-2.0 — `ADAPT`
**Механизм.** Би-темпоральный граф: у каждого ребра есть окно валидности, поэтому «истина вчера» не перезаписывается сегодняшней. Гибридный поиск: семантика + BM25 + переходы по графу. ~27.7k звёзд, Apache-2.0 (проверено поиском 2026-11-03).
**Почему для NK1.** В `MemoryOS2` уже есть `temporalLinks` и `validFromAt`/`validUntilAt`, но нет модели, где ребро связи имеет собственное окно и версию. Это прямо закрывает потребность «помнить, что изменилось», а не только «что есть».
**Граница.** Не вендорить движок и не поднимать Neo4j. Адаптировать модель: добавить к связям `validFrom`/`validUntil`/`supersedesId` в `MemoryOS2` и включить их в ранжирование.
**Польза (гипотеза).** Рост точности на вопросах с изменением факта во времени. Не заявлять без прогона.
**Риск.** Дублирование владельца памяти — прямое нарушение правила «один владелец». Только адаптация модели, не второй стор.
**Тест.** Пара запросов «значение до изменения» / «после» на неизменяемом holdout; baseline — текущий `MemoryOS2`.
**Решение.** `ADAPT` (модель). Вендоринг кода — `REJECT`.

### C2. Zep Community Edition — `REJECT` (вендоринг)
**Причина.** CE прекращён в 2026; ядро памяти стало закрытым. Берём только идеи из Graphiti.

### C3. Mem0 (`mem0ai/mem0`) — Apache-2.0 — `ADAPT`
**Механизм.** Пассивное извлечение фактов из диалога + векторный и графовый слой; полностью self-hostable.
**Почему.** У NK1 консолидация есть, но извлечение фактов из свободного текста слабое.
**Граница.** Адаптировать контракт извлечения (кандидат → подтверждение → запись), не переносить стор.
**Риск.** Vendor-числа: LongMemEval 94.4 у Mem0 против 49.0 при независимом прогоне. Любая цифра отсюда — не доказательство.
**Решение.** `ADAPT`.

### C4. Letta / MemGPT (`letta-ai/letta`) — Apache-2.0 — `ADAPT`
**Механизм.** Память как ОС: core (RAM), recall (кэш), archival (холод); агент сам редактирует блоки через tool-calls. Apache-2.0 с 2024, не менялась.
**Почему.** NK1 нуждается в саморедактируемой памяти с явным контролем, кто и когда редактирует.
**Граница.** Адаптировать тир-модель и контракт self-edit, но **каждое** саморедактирование памяти проходит через `SelfModificationGuard` (файл не защищённый — редактирование допустимо, но логируется).
**Риск.** Саморедактирование памяти — новый вектор ошибок; нужен лимит и откат.
**Решение.** `ADAPT`.

### C5. Cognee (`topoteretes/cognee`) — Apache-2.0 — `EVALUATE`
**Механизм.** ECL (extract-cognify-load) пайплайны, взаимозаменяемые бэкенды (Neo4j, Neptune, relational).
**Решение.** `EVALUATE` только как источник паттернов пайплайна.

### C6. LangMem / LangGraph — MIT — `EVALUATE`
Паттерн store/namespace. Применим к организации долгой памяти, но тянет зависимость LangGraph. Пока `EVALUATE`.

### C7. Supermemory — MIT (core) — `EVALUATE`
Локально запускаемый. Проверить на локальном holdout, не на vendor-числах.

### C8. Hindsight — MIT — `EVALUATE` (с оговоркой)
Заявляет 94.6% LongMemEval; это **vendor-run**, независимой проверки нет. Берём только идею cross-encoder реранка — и только если он реально доступен локально.

## 3. Самоулучшение и отбор кандидатов

### C9. OpenEvolve (`algorithmicsuperintelligence/openevolve`) — Apache-2.0 — `ADOPT`
**Механизм.** Открытая реализация AlphaEvolve: prompt sampler (прошлые программы + их оценки), LLM-ансамбль, evaluator pool, program database с островной/бандитской селекцией. Мутация ограничена блоками `EVOLVE-BLOCK-START/END`. ~7.6–7.7k звёзд, Apache-2.0.
**Почему это главный кандидат.** `SandboxedSelfRewriteEngine.ts` — 4 строки, то есть механизма нет вообще. OpenEvolve даёт ровно недостающие части: пул кандидатов, отбор по измеренному скору, ограничение области мутации.
**Граница.** Реализовать цикл в NK1 (не вендорить Python), но перенести архитектуру:
1. `EVOLVE-BLOCK` — мутировать разрешено только внутри маркированных блоков; остальное — заморожено;
2. пул кандидатов с историей скоров;
3. отбор по измеренному downstream-скору.
**Критично.** Скор кандидата проходит через `ProxyDivergenceGuard` (уже реализован): proxy-выигрыш без downstream-выигрыша отклоняется. Evaluator-файлы недостижимы для мутации через `SelfModificationGuard`.
**Тест.** Кандидат, улучшающий proxy и не улучшающий downstream, обязан быть отклонён; кандидат вне `EVOLVE-BLOCK` обязан не применяться.
**Решение.** `ADOPT` (архитектура). Это самый большой незакрытый разрыв.

### C10. OpenAlpha_Evolve (`shyamsaktawat/OpenAlpha_Evolve`) — MIT — `EVALUATE`
Тот же класс, MIT. Резервный источник, если OpenEvolve окажется неприменим.

### C11. AIDE² и протоколы held-out selection — `ADOPT` (протокол)
**Механизм.** Отбор кандидатов по производительности на отложенном наборе, а не по обучающему сигналу; узкое место самоулучшения — именно отбор, а не генерация.
**Почему.** Прямо отвечает на «ускорение самообучения»: ускоряет не генерация вариантов, а качественный отбор.
**Решение.** `ADOPT` как протокол: каждый кандидат оценивается на holdout, недоступном оптимизатору.

### C12. METR RE-Bench — `ADOPT` (протокол оценки)
Использовать как ориентир для проверки, что «улучшение» не артефакт метрики.

## 4. Анализ кода и понимание опасности

### C13. tree-sitter (`tree-sitter/tree-sitter`) — MIT — `ADOPT`
**Механизм.** Инкрементальный парсер, строит конкретное синтаксическое дерево; S-expression запросы для анализа. 0.27.1 (окт 2026), ~27.3k звёзд, MIT.
**Почему.** Текущий `SourceGraph.ts` — regex + глубина скобок. Он детерминирован и без зависимостей, но не различает, например, `class` внутри типа-литерала. tree-sitter даёт точные границы и типы узлов.
**Граница.** Как **dev-зависимость** инструмента анализа, не в рантайме. `SourceGraph.ts` остаётся fallback без зависимостей; tree-sitter — уточняющий проход, когда доступен.
**Риск.** Нативные бинарники/грамматики. Не тянуть в рантайм, где запрещены native-модули.
**Тест.** Совпадение границ символов на наборе файлов; при отсутствии tree-sitter — работа через fallback.
**Решение.** `ADOPT` (dev-only).

### C14. Semgrep — LGPL-2.1 — `EVALUATE` (лицензия под вопросом)
**Механизм.** Статический анализ по паттернам; можно искать опасные вызовы (eval, shell, файловые записи) в обработчиках действий.
**Почему.** Прямо про «понимание опасности»: автоматически находить опасные sink-и в новом коде.
**Риск.** LGPL — обязательства при распространении. Не вендорить в продукт; использовать как внешний dev-инструмент.
**Решение.** `EVALUATE`.

### C15. CodeQL — `EVALUATE` (лицензия ограничена для OSS)
Использовать как внешний сканер в CI, не как часть продукта.

## 10. Требование к доказательствам

Для каждого внедрённого пункта обязательно:
1. baseline и кандидат на **одном** корпусе и одном holdout;
2. downstream-метрика, не только proxy;
3. абляция (что именно дало эффект);
4. лицензия перепроверена и записана;
5. откат проверен.

Без этого пункт остаётся `EVALUATE`, а не `ADOPT`.
