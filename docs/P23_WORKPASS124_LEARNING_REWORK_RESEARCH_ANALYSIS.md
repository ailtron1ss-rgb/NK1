# WorkPass124 — анализ переработки обучения и план закрытия рисков

Дата анализа: 2026-10-21. База: WorkPass123, commit `21fef8029b7329f438276c915ce1139c4dfff093`.
Этот документ разделяет уже реализованные механизмы, инженерные риски и эмпирические утверждения. Он не объявляет тесты пройденными и не выдаёт архитектурные оценки за результаты бенчмарков.

## 1. Что уже изменено в цепочке обучения

В текущей ветке накоплены следующие механизмы:

1. **Многоисточниковое обучение и отбор опыта** — отдельные механизмы для извлечения повторно используемых навыков, рефлексии над исходом, построения curriculum и контроля допуска replay.
2. **Воспроизводимость экспериментов** — план эксперимента, учёт исполнения, seed-clustered сравнение исходов и аудит полноты evidence.
3. **Проверяемость исходов** — ledger связывает результаты с задачей/версией/методом/seed; подписанный артефакт требует доверенного ключа, совпадения manifest и корректной подписи.
4. **Контроль распространения навыков** — proposal gate, candidate store с версиями, shadow runs, явное одобрение, CAS, сохранение предыдущей версии и rollback.
5. **Отчётность без ложного агрегата** — качество навыка, траектория исполнения и подтверждённые исходы представлены отдельными измерениями.
6. **Персистентность** — файловый адаптер пишет через временный файл, fsync и атомарный rename под lock; адаптер всё ещё нуждается в тестах гонок и проверки на целевых ОС.

Это значимый переход от «модель сказала, что научилась» к управляемому циклу «опыт → доказательства → кандидат → изолированная оценка → одобрение → развёртывание → откат».

## 2. Сопоставление с опубликованными направлениями

### SkillLearnBench (COLM 2026)

Репозиторий описывает 20 задач, 15 поддоменов, 100 проверяемых экземпляров и три уровня оценки: успех задачи, качество навыка и качество траектории. В качестве сравнений предусмотрены no-skill, human-authored, one-shot, self-feedback, teacher-feedback и Skill Creator.

**Адаптация в NK1:** три уровня отчёта и раздельная оценка verified outcomes уже согласуются с идеей не сводить обучение к одному pass rate. Следующий необходимый шаг — реальный адаптер набора задач/верификаторов или внутренний benchmark, повторяющий эти уровни, с holdout-экземплярами. Пока не запускали внешний benchmark, нельзя заявлять сопоставимый результат.

Источник: https://github.com/cxcscmu/SkillLearnBench  
Статья: https://arxiv.org/abs/2604.20087

### Memento-Skills (2026)

Проект формулирует deployment-time learning как цикл Read → Execute → Reflect → Write, с навыками как версионируемыми единицами, локальным исполнением, изолированным обновлением, автоматическими воротами и откатом. Описанная схема оставляет параметры базовой модели замороженными и накапливает опыт во внешней памяти навыков.

**Адаптация в NK1:** retrieval/reflection/curriculum, candidate lifecycle, shadow evaluation и rollback реализуют похожие инженерные идеи, но в рамках текущей архитектуры NK1. Код Memento-Skills не копировался в этом проходе; это архитектурное сопоставление, а не заявление о прямом переносе исходников. Следует сравнить точные контракты навыков, безопасность sandbox, маршрутизацию и восстановление после сбоя, прежде чем портировать любой файл.

Источник: https://github.com/Memento-Teams/Memento-Skills  
Статья: https://arxiv.org/abs/2603.18743

## 3. Что сделано правильно — и где есть существенные пробелы

### Сильные стороны
- Не активировать новый навык автоматически только на основании self-report.
- Отделить proposal, shadow-проверки и явное одобрение.
- Проверять происхождение signed outcomes и не считать восстановленный snapshot доказательством подписи.
- Использовать версионность, ожидаемую активную версию и rollback.
- Не смешивать skill quality, trajectory quality и task success в непрозрачный общий балл.
- Использовать сравнение по задачам/seed, а не только общую среднюю величину.

### Риски, которые остаются открытыми
1. **Нет доказанной production-подключённости.** Lifecycle в P23LearningEngine включается через явный configure; без конфигурации приложения основной runtime продолжает использовать прежний путь.
2. **Shadow evidence пока недостаточно аутентифицировано.** Store проверяет форму fingerprint и run ID, но одной 64-символьной строки недостаточно, чтобы доказать, что исход реально получен доверенным исполнителем. Нужен signed execution artifact с привязкой к candidate ID, run ID, task/manifest, seed, версии runtime и исходу; проверка должна быть внутри границы доверия store.
3. **Происхождение outcomes process-local.** После рестарта подписанные артефакты необходимо заново верифицировать. Это безопаснее, чем слепо доверять snapshot, но требует загрузочного re-verification pipeline и наблюдаемого состояния «evidence не восстановлено».
4. **Файловый CAS не доказан для всех сред.** Нужны конкурентные процессы, аварийное завершение в каждой точке записи, восстановление stale lock, повреждённый JSON, Windows/macOS/Linux и повторное открытие после рестарта.
5. **Нет подтверждённого CI.** Последние GitHub Actions runs завершались до появления job steps (runner_id=0, steps=[]). Это похоже на provisioning/environment issue, но не доказывает корректность исходников. Пока workflow не исполнит команды, статус тестов — «не подтверждён».
6. **Нет измеренного прироста обучения.** Архитектурная полнота не равна улучшению качества. Нужны baseline no-skill/context-only, текущий NK1, skill reuse, ablation по retrieval/reflection/curriculum и независимый holdout.
7. **Защита от загрязнения данных и reward hacking.** Верификатор может быть ошибочным или предвзятым даже при валидной подписи; нужна ротация ключей, аудит доверенных verifier ID, лимиты повторов, детект дубликатов и независимый контроль выборки.
8. **Transfer/retention/forgetting.** Нужно измерять перенос на новые задачи, удержание после задержки и interference после обучения смежным навыкам; повторное решение тех же примеров не является доказательством обобщения.

## 4. Предлагаемый протокол измерения

Каждый эксперимент должен фиксировать commit, модель/провайдера, prompt/config fingerprint, версии навыков, набор задач и verifier, seeds, число попыток, стоимость/токены, время, ошибки и подписанные результаты.

Сравнивать на одних и тех же задачах и seed:
- A: no-skill / только базовый контекст;
- B: текущая библиотека навыков без записи нового опыта;
- C: полный цикл NK1;
- D: ablation без reflection;
- E: ablation без curriculum/retrieval;
- F: human-authored skills как верхний ориентир, если доступен и лицензия позволяет.

Основные метрики:
- task success rate и парная разница с доверительным интервалом;
- skill functional coverage / executability / safety;
- trajectory key-point recall / order / completeness;
- transfer на невиданные экземпляры и соседние задачи;
- retention после фиксированной задержки и после interference tasks;
- число ложных promotion, rollback rate и регрессии;
- стоимость успешной задачи, latency и число повторных попыток.

Seeds одного задания нельзя считать независимыми заданиями. Публиковать число уникальных task instances, число запусков и интервалы неопределённости. Не допускать попадания verifier/ответов holdout в генерацию навыков.

## 5. Критерии завершения для следующего инженерного цикла

- [ ] Доверенная подпись shadow-run артефакта, связанная с candidate/task/seed/commit, обязательна для promotion.
- [ ] Bootstrap приложения явно создаёт durable store по конфигурации, с безопасным отказом при ошибочной конфигурации; ephemeral режим должен быть явным.
- [ ] На старте проводится re-verification signed outcome artifacts; неподтверждённые записи не участвуют в promotion.
- [ ] Тесты crash/restart/contention запускаются на реальных runners минимум Linux и Windows.
- [ ] Workflow выполняет typecheck и весь набор P23 regressions; статус CI зелёный на точном HEAD.
- [ ] Запускается benchmark с no-skill и ablation baseline; публикуются исходные отчёты и конфигурация.
- [ ] Выполняются transfer/retention/interference проверки на holdout.
- [ ] Лицензии, provenance и границы переноса внешних исходников фиксируются для каждого реально портируемого компонента.

## 6. Итоговая оценка

Текущая переработка улучшает **управляемость жизненного цикла навыков и происхождение доказательств**, а не доказывает, что NK1 уже учится лучше известных систем. Ключевой архитектурный пробел — отсутствие доказанного end-to-end пути от реального execution runner к аутентифицированному shadow evidence и production bootstrap. Ключевой научный пробел — отсутствие измерения против контрольных условий. До закрытия этих двух пробелов любые числовые оценки зрелости остаются инженерными экспертными оценками, а не benchmark score.
