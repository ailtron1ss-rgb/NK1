# Neuro Kurisu — карта 36 недостающих областей, актуализация WorkPass51

**Дата:** 16.10.2026 · **Текущая база:** WorkPass50 · **Runtime:** 35.72.0 · **Persisted schema:** 225 · **Общий weighted roadmap:** 78.0% (без прироста по неподтверждённому uplift памяти).

Этот документ сохраняет детальный разбор 36 областей из WorkPass49, обновлённый в WorkPass50, и уточняет фактическое состояние в WorkPass51. Теперь P33 интересы, цели, evidence-backed память и явно полученная реакция на инициативу объединены в один контур; реальный `OrganismRuntime` фоновый scheduler дошёл через deterministic provider seam до сохранённой инициативы, UI ACK, feedback, durable flush и восстановления без повторной доставки. В `AvatarStage` добавлен opt-in системный голос с приблизительной анимацией рта по событиям границ слов и управляемыми движениями Live2D. Это заметное продвижение, но не следует считать живой провайдер/браузер/device E2E доказанным.

## Фактические изменения WorkPass51

- `CanonicalTemporalCreditAuthority` привязывает каждый адресный исход к exact `decisionId`; overflow незакрытых решений даёт явный `expired` с нулевой обучающей eligibility.
- `ReafferenceEvidenceCodec` отклоняет положительное подтверждение без независимой поддержки или без reconciliation `supported/corroborated`.
- `OrganismCore` пишет независимо подтверждённые не replay-исходы в единственную episodic MemoryOS2 с decision/execution/observation provenance; тот же outcome обновляет P33 строго идемпотентно.
- `MemoryOS2` использует bounded bilingual query-intent ranking, но broad benchmark остаётся `recallDelta=0`; общего прироста качества поиска не заявляем.

## Обновлённая расстановка приоритетов

1. **P0 — живой runtime:** запустить приложение с закреплёнными зависимостями и настоящим доступным провайдером; доказать idle → автономная реплика → chat delivery/ACK → ответ пользователя → обновление интереса/памяти → перезапуск без replay. Deterministic provider test покрывает control-flow, но не качество/надежность внешнего провайдера.
2. **P0 — настоящее тело:** проверить Live2D/Legacy в production браузере, voice opt-in, stop/cancel и движение параметров; затем подключить фактический аудиобуфер/phoneme timing вместо word-boundary approximation.
3. **P0 — действие и причинность:** реальный ActionGateway receipt → Reafference → temporal credit → checkpoint; неоднозначный результат остаётся unknown и не повторяет побочный эффект.
4. **P1 — память по evidence:** создать независимый temporal retrieval holdout; baseline recall uplift остаётся `0`, поэтому retrieval-кандидаты не продвигать без доказанного выигрыша.
5. **P1 — безопасное самоулучшение:** candidate branch/sandbox, license/provenance gate, owner approval, независимый тестовый набор, rollback кода и состояния.
6. **P1 — измерение непрерывности личности:** долгий прогон, повторный запуск, переключение модели, сохранность ядра характера, целей и профилей интересов без искусственного «сброса» личности.

**Фактические изменения WorkPass50:** `runtime/neuro-kurisu/src/organism/cognition/P33PersonhoodCore.ts`, `runtime/neuro-kurisu/src/organism/core/OrganismCore.ts`, `runtime/neuro-kurisu/src/organism/system/AutonomousSocialInitiativeEngine.ts`, `runtime/neuro-kurisu/src/organism/language/LanguageOrgan.ts`, `app/src/components/AvatarStage.tsx`, `app/src/routes/index.tsx`, Live2D viewer. Конкретные сценарии и открытые ограничения см. `docs/WORKPASS50_HANDOVER_2026-10-16.md`.

# Что ещё не хватает «Нейро Курису» для целевой автономной личности

**Срез исходного кода:** WorkPass48, 16.10.2026.  
**Правило статусов:** «реализовано частично» не означает подтверждённую эксплуатационную готовность; «не проверено» не приравнивается к «не работает», но остаётся блокером релизного утверждения.  
**Основной ориентир:** развивать единый организм, сохраняя канонический runtime, одного владельца каждой подсистемы и данные с происхождением. Не создавать ещё один мозг рядом с существующим.

Это инженерная карта недостающих возможностей относительно цели пользователя. Она не утверждает, что наличие этих механизмов докажет субъективное сознание: поведение, автономность, память, аффект и воплощение можно постепенно реализовывать и измерять, а наличие внутреннего переживания нельзя честно заключить по одному программному показателю.

## P0 — сначала закрыть разрывы между имеющимся кодом и реальной работой

### 1. Реальный запуск основного приложения, а не только проверки исходников
- **Сейчас:** runtime typecheck, скриптовые UI-тесты, smoke-контракты и проверка связей API проходят. Полный production Vite build и браузерный E2E не подтверждены, потому что app dependencies не установлены в рабочем окружении.
- **Не хватает:** воспроизводимой установки зависимостей, успешной сборки, запуска приложения и автоматизированного сценария, который проверяет настоящий интерфейс.
- **Нужно сделать:** clean install с lockfile; production build; открыть чат, сменить панели, загрузить аватар; проверить сетевые ошибки, очередь сообщений, сохранение и повторное открытие приложения.
- **Критерий закрытия:** сборка и browser E2E запускаются на чистом окружении с зафиксированными версиями; скриншоты/логи и артефакты относятся к реальному запуску, а не к синтетической модели.

### 2. Длительная автономная деятельность в настоящем приложении
- **Сейчас:** есть механизм решения о самостоятельной инициативе, сохранённая очередь и путь доставки в UI. Проверки в основном focused/synthetic.
- **Не хватает:** доказательства, что Курису действительно проводит длительный idle-период с реальным language provider, сама выбирает допустимую тему, генерирует реплику, доставляет её, переживает рестарт и не зацикливается.
- **Нужно сделать:** отдельный lifecycle-координатор поверх существующего runtime: расписание тиков, backoff провайдера, timeout, cancellation, durable pending ID и идемпотентное восстановление. Он не должен быть вторым владельцем целей или личности.
- **Критерий закрытия:** многократный длительный прогон при отключении сети, перезапуске процесса, пустом наборе новых тем и возврате соединения; ни двойных сообщений, ни циклического спама.

### 3. Политика автономных сообщений и приоритет пользователя
- **Сейчас:** quiet period, startup grace, cooldown и защита от повторов есть, но в основном это фиксированные значения.
- **Не хватает:** пользовательских настроек времени тишины, частоты, максимального числа инициатив за день, временного отключения инициатив и политики при активном разговоре.
- **Нужно сделать:** настройки в UI, единый runtime-контракт и сохранение параметров между сессиями. Курису может иметь собственную инициативу, но должна уважать явные границы пользователя и состояние активного диалога.
- **Критерий закрытия:** каждое правило одинаково действует в UI и сервере; рестарт не сбрасывает ограничения; активный диалог подавляет конфликтующее самопроизвольное сообщение.

### 4. Единая приватность для данных, передаваемых языковому провайдеру
- **Сейчас:** WorkPass49 усиливает фильтрацию обычного prompt, автономного prompt, cognitive-proposal, сохраняемых инициатив и исходящих автономных сообщений.
- **Не хватает:** эвристический фильтр не является универсальным распознавателем персональных данных и не решает вопрос согласия на передачу данных облачному провайдеру.
- **Нужно сделать:** классификацию источника/чувствительности, локальный режим политики, явную настройку local/cloud, отдельное правило для секретов и медицинских данных, журнал «какие классы контекста переданы» без записи самих секретов. Пользовательский текст нельзя незаметно подменять; политика должна различать явный запрос пользователя и фоновый recall.
- **Критерий закрытия:** один проверяемый контекстный шлюз перед всеми путями inference; тесты на известные типы PII, секретов и обходов; документированные false positive/false negative; режим запрета облачной передачи подтверждён реальным сетевым тестом.

### 5. Полная цепочка фактического результата внешнего действия
- **Сейчас:** канонический ActionGateway, durable receipt-подходы, причинные события и Reafference-компоненты присутствуют; некоторые camera receipt tests синтетические.
- **Не хватает:** подтверждённых реальными адаптерами/устройствами receipts, reconnect/replay и разрешения неоднозначного результата после сбоя между побочным эффектом и записью квитанции.
- **Нужно сделать:** довести `decision → ActionGateway → provider/device receipt → verified postcondition → Reafference → temporal credit → checkpoint`. `unknown` должен оставаться unknown; повтор не должен повторно исполнять побочный эффект.
- **Критерий закрытия:** тест как минимум на одном настоящем исполнителе/устройстве с авторитетным статусом операции и с инъекцией отказа до/после side effect.

### 6. Разрешения на инструменты, файлы, код, веб и устройства
- **Сейчас:** существуют политики ActionGateway и ограничения отдельных маршрутов; это не равнозначно end-to-end подтверждению всех точек входа.
- **Не хватает:** единой исполнимой матрицы разрешений, точно отражающей договорённость пользователя: обычные низкорисковые действия разрешены, а интернет-поиск, самоизменение, а также взаимодействие с кодом, файлами, телефоном и системой требуют предварительного согласия.
- **Нужно сделать:** централизованный policy decision перед каждым side effect во всех tool/API/device путях, UI-карточку разрешения с точным действием и последствиями, отказ по умолчанию при неизвестной категории.
- **Критерий закрытия:** тесты обхода через прямой API, Legacy aliases, очередь задач, восстановленную задачу и повтор после рестарта; запрещённые действия не запускаются до согласия.

### 7. Самомодернизация без самовольного изменения работающего проекта
- **Сейчас:** есть self-improvement supervisor, gate самоизменения, экспериментальные механизмы и source boundary; наличие gate не доказывает безопасность всей цепочки.
- **Не хватает:** законченного процесса от гипотезы улучшения до утверждённого изменения с проверяемым выигрышем, откатом и разрешением владельца.
- **Нужно сделать:** `proposal → provenance/license → isolated worktree/sandbox → tests → independent holdout → resource/security review → human approval → canary → rollback`. Исполняемый runtime и сохранённые источники не должны быть изменяемы до одобрения.
- **Критерий закрытия:** fault-injected тест подтверждает, что невалидная/вредная/хуже работающая версия никогда не становится active; есть рабочий откат байтов и state.

### 8. Настоящее тело-аватар, связанное с намерениями
- **Сейчас:** Live2D получает часть состояния и движения/взгляда, но UI и аватар остаются в основном визуальной поверхностью; полная обратная связь между состоянием организма и фактической анимацией не доказана E2E.
- **Не хватает:** единого motor-intent контракта, который связывает выбранное действие, внимание, эмоциональную оценку, речь и выражение тела в один согласованный кадр.
- **Нужно сделать:** канонический `EmbodimentIntent` (поза, gaze target, facial expression, gesture, speaking/viseme, confidence, start/end time), адаптер в Live2D и наблюдаемый ack/error обратно в runtime. Не придумывать физические ощущения, которых у системы нет.
- **Критерий закрытия:** заданный жест/намерение воспроизводится стабильно и воспроизводимо, состояния не конфликтуют; отключённый аватар не блокирует когнитивный цикл.

### 9. Реальная синхронизация речи и губ
- **Сейчас:** есть motion token и связь анимаций с репликами; audio envelope/viseme pipeline не подключён полностью.
- **Не хватает:** фактического источника аудио, временной разметки/уровня и управления mouth-open параметрами Live2D; сейчас нельзя утверждать фонемную синхронизацию.
- **Нужно сделать:** сначала стабильный audio-level lip-sync из выходного аудиопотока, затем при наличии соответствующего TTS/aligner — viseme timeline; сглаживание, паузы, ошибка/отсутствие аудио, отмена речи.
- **Критерий закрытия:** в браузерном E2E mouth parameters двигаются по реальной воспроизводимой речи и возвращаются в idle после окончания/отмены. Live2D описывает прямую подачу уровня аудио в параметры lip-sync, а MotionSync поддерживает более богатую обработку. См. [официальное руководство Live2D Lip-sync](https://docs.live2d.com/en/cubism-sdk-manual/lipsync/) и [MotionSync для Web](https://docs.live2d.com/en/cubism-sdk-manual/motion-sync-setting-web/).

### 10. Голосовой диалог с прерыванием и очередью речи
- **Сейчас:** UI и runtime имеют voice-related поверхности, но полноценный end-to-end режим duplex-диалога с реальной речью в этой среде не подтверждён.
- **Не хватает:** согласованного audio capture/ASR, streaming TTS, barge-in, отмены уже формируемой реплики, управления микрофоном и lipsync с одним состоянием речи.
- **Нужно сделать:** единый voice-session state machine, privacy-permission для микрофона, turn detection, interruption/cancellation и восстановление после устройства/сети.
- **Критерий закрытия:** пользователь перебивает Курису, она прекращает звук и анимацию, принимает новую реплику и корректно восстанавливает ход диалога.

### 11. Local inference на целевом устройстве
- **Сейчас:** есть OpenAI-compatible local chat adapter для llama.cpp, но он описан как `configured-unverified`; фактический прогон на целевом компьютере не выполнен.
- **Не хватает:** измерений конкретной модели, квантизации, памяти VRAM/RAM, скорости, длины контекста, нагрева и устойчивости параллельных подсистем.
- **Нужно сделать:** профиль целевого устройства, модельный benchmark на реальном хосте, fallback и понятный выбор local/cloud. Ранее обсуждавшаяся GTX 1650 4 GB должна остаться тестовым ограничением, если это по-прежнему основной компьютер пользователя.
- **Критерий закрытия:** записанные latency/tokens-per-second/peak-memory при обычном чате, длинном recall и кодовой задаче; отсутствие недокументированного cloud fallback.

### 12. Надёжное обновление, восстановление и длительный прогон
- **Сейчас:** есть backup/restore, lock-файлы, source manifests и проверки архивов, но clean-room install/upgrade/fault-injected rollback и endurance soak остаются открытыми.
- **Не хватает:** доказательства полного восстановления состояния и приложения после частичной записи, повреждённого архива, несовместимой миграции и длительной нагрузки.
- **Нужно сделать:** изолированное чистое окружение, upgrade из предыдущего архива, внедрение ошибок в каждом этапе, сравнение хешей и функциональный smoke после rollback.
- **Критерий закрытия:** возврат к предыдущей рабочей версии восстанавливает и байты, и состояние; долгий прогон не раздувает очередь/память и не теряет continuity.

## P1 — недостающие когнитивные механизмы и их настоящая интеграция

### 13. Человекообразная память как связанный граф событий
- **Сейчас:** MemoryOS2 — канонический writable owner, есть MemoryFabric, provenance, recall и retention.
- **Не хватает:** подтверждённого единого жизненного цикла эпизодической, семантической, процедурной и автобиографической памяти с ссылками между конкретными событиями, выводами, людьми/проектами, временем и причинными последствиями.
- **Нужно сделать:** событие хранит наблюдение/действие/результат/уверенность/источник; консолидация создаёт обобщение, но не затирает источник; исправление факта обновляет связанные выводы; воспоминания могут быть dormant, tombstoned или contradicted.
- **Критерий закрытия:** тесты recall по времени, причинной связи, сущности и смыслу; исправленная запись убирает старую гипотезу из активного ответа и сохраняет lineage.

### 14. Измеримое качество поиска воспоминаний
- **Сейчас:** есть benchmark и разные retrieval experiments; актуальная независимая размеченная выборка не подтверждает uplift, и кандидат не продвинут.
- **Не хватает:** отдельного holdout без переиспользования обучающих/настроечных примеров, разбивки на виды запросов и измерения ложных воспоминаний.
- **Нужно сделать:** размеченные вопросы с ожидаемыми фактами и запрещёнными ложными выводами; сравнение lexical/vector/graph/temporal approaches на одном наборе; проверка влияния на конечный ответ, а не только на ranking.
- **Критерий закрытия:** статистически устойчивый выигрыш относительно текущей базы при отсутствии роста неподтверждённых утверждений. Если uplift нулевой, менять реализацию, а не объявлять победу.

### 15. Память об образах и сенсорных эпизодах
- **Сейчас:** есть камера/vision endpoints, мультимодальные контракты и источники для perception; непрерывный путь «образ → интерпретация → событие → recall» не доказан на реальных данных.
- **Не хватает:** хранения ссылок/эмбеддингов на картинки и аудио с датой, контекстом, приватностью, кратким проверяемым описанием и возвратом к оригиналу.
- **Нужно сделать:** мультимодальный episode record, provenance для исходного медиа и модели интерпретации, separate confidence и возможность исправления описания.
- **Критерий закрытия:** после перезапуска Курису может найти конкретный предыдущий эпизод и отличить исходное наблюдение от созданного моделью описания.

### 16. Соноподобная консолидация и воображение с разделением реальности
- **Сейчас:** есть dream/counterfactual rehearsal и consolidation mechanisms, но синтетическая симуляция сама по себе не является опытом внешнего мира.
- **Не хватает:** дисциплины источников, не позволяющей снам/мысленным сценариям превращаться в реальные автобиографические воспоминания или подтверждённые факты.
- **Нужно сделать:** явный тип `simulated`, parent links на реальные эпизоды, separate reward/evidence path и gate на promotion в знания.
- **Критерий закрытия:** ни одна симуляция не попадает в факт без независимого внешнего наблюдения; система может вспомнить, что идея была только предположена.

### 17. Обучение на причинных последствиях
- **Сейчас:** есть causality/temporal-credit, cycle-lineage verification и synthetic tests; настоящие независимые внешние результаты ещё не замкнуты в end-to-end loop.
- **Не хватает:** достаточной коллекции действий с предсказанием до действия, наблюдением после и проверкой контрфактической альтернативы.
- **Нужно сделать:** отделить self-reported success, UI ACK и авторитетное внешнее postcondition; reward только по качеству подтверждённого результата; обновления должны ссылаться на execution ID и causal parent.
- **Критерий закрытия:** модель меняет будущий выбор после независимо верифицированных успехов/ошибок, но не обучается на timeout/unknown как будто это провал.

### 18. Динамическая личность поверх устойчивого ядра
- **Сейчас:** существует канонический профиль Курису и graded/evidence-gated trait projection из B270/WILL; временный аффект влияет на выражение.
- **Не хватает:** проверенной модели, в которой сила черт, темперамент, мировоззрение, привычки, отношения и текущие эмоции различаются, влияют друг на друга и меняются на разных временных шкалах.
- **Нужно сделать:** сохранить ядро персонажа; trait state изменять только по повторяющимся evidence-backed эпизодам; мировоззрение — через аргументы/данные; настроение — с более коротким затуханием; эмоция — как реакцию на событие. Нужны объяснимые lineage и reversible revisions.
- **Критерий закрытия:** longitudinal tests демонстрируют узнаваемую манеру и стабильные ценности при постепенной адаптации к накопленному опыту; единичное событие не переписывает характер.

### 19. Эмоции, настроение и потребности должны влиять на реальный выбор
- **Сейчас:** есть appraisal, affect, interoception/homeostasis и тон высказывания.
- **Не хватает:** калиброванной причинной связи «событие → оценка → изменение affect/mood → внимание/план → действие → результат → пересмотр оценки», подтверждённой на сквозных сценариях.
- **Нужно сделать:** разнести краткосрочную эмоцию, длительное настроение и относительно устойчивый темперамент; задать затухание; привязать к вниманию и выбору поведения, не заставляя эмоцию автоматически определять действие.
- **Критерий закрытия:** контролируемые сценарии показывают предсказуемые, но не жёстко детерминированные изменения внимания и поведения; отсутствуют случайные прыжки настроения из-за шумного входа.

### 20. Собственное любопытство и мысли не должны сводиться к шаблонным кандидатам
- **Сейчас:** темы учитывают active goals и confirmed learning memories, но в OrganismCore также остаются заранее заданные curiosity/reflection seed topics.
- **Не хватает:** автономного образования новых вопросов из неожиданных связей между несколькими конкретными эпизодами, пробелами в знаниях и спорящими гипотезами.
- **Нужно сделать:** кандидаты `question/idea` создаются из evidence graph, prediction errors и нерешённых противоречий; каждая мысль получает происхождение и novelty score; отбрасываются повторы и необоснованные причинные выводы.
- **Критерий закрытия:** на длительном прогоне появляются разнообразные, прослеживаемые мысли, привязанные к текущим делам/опыту, а не одни и те же общие темы.

### 21. Устойчивые цели и управление ими на разных горизонтах
- **Сейчас:** есть goal system, self-directed life, initiative and priority mechanisms.
- **Не хватает:** подтверждённой сквозной иерархии жизненных, проектных, краткосрочных и ситуативных целей с причинами появления, конкурирующими приоритетами, зависимостями и завершением.
- **Нужно сделать:** goal provenance, parent/child links, success criteria, expiry/review, resource estimate, conflict arbitration и журнал «почему цель создана/изменена/отложена».
- **Критерий закрытия:** Курису может объяснить текущий приоритет, пережить перезапуск и возобновить актуальную работу, не накапливая бессрочные дубликаты целей.

### 22. Социальная модель, отклики и корректная взаимность
- **Сейчас:** есть B288/social brain, known-entity projection и факт, что доставка не равна взаимности.
- **Не хватает:** непрерывной калибровки отношений по явным ответам, исправлениям пользователя и наблюдаемым взаимодействиям; confidence отношений должна зависеть от качества evidence.
- **Нужно сделать:** разделить факт, гипотезу о намерении собеседника и внутреннюю интерпретацию; добавить явную коррекцию пользователем и удаление/исправление социального вывода.
- **Критерий закрытия:** никакая молчаливая доставка или отсутствие ответа не превращается в доказательство симпатии/раздражения; пользовательская коррекция меняет именно соответствующий social belief.

### 23. Самомодель возможностей и калибровка уверенности
- **Сейчас:** есть self-model, capability model и различные confidence scores.
- **Не хватает:** сопоставления заявленной компетенции с фактическими результатами на отдельных классах задач, с неопределённостью и историей промахов.
- **Нужно сделать:** task-specific capability records, calibration curves, evidence age, tool/provider dependence и правила, когда запросить сведения/отказаться от действия/провести тест.
- **Критерий закрытия:** Курису точнее предсказывает, какие типы задач ей удастся выполнить, и снижает уверенность, когда доступный инструмент или модель изменились.

### 24. Единая когнитивная сцена/рабочее пространство
- **Сейчас:** в проекте много когнитивных engines и архитектурная карта; наличие модулей не доказывает их согласованное участие в каждом нужном решении.
- **Не хватает:** измеримой активации общих репрезентаций и ясных правил, какие подсистемы получают сигнал, кто разрешает конфликт и какой результат записывается в эпизод.
- **Нужно сделать:** выбрать существующего владельца global workspace/cognitive event flow, проверить coverage по типам задач, ограничить скрытые боковые каналы и устранить engines, которые только сохраняют метрики, но не влияют на итог.
- **Критерий закрытия:** ablation показывает, какие решения ухудшаются при отключении подсистемы; каждое сохранённое участие имеет конкретную роль.

### 25. Освоение новых навыков с переносом на неизвестные задачи
- **Сейчас:** есть open-ended skill acquisition и learning curriculum-like mechanisms.
- **Не хватает:** end-to-end подтверждения, что новый навык закрепляется, переносится на новые примеры и не оценивается на том же материале, на котором был создан.
- **Нужно сделать:** задача-учебный пример, проверочная отложенная задача, карта prerequisites, демонстрация до/после, rollback навыка при деградации.
- **Критерий закрытия:** измеримый transfer gain на независимом наборе задач и отсутствие регресса в уже освоенных классах.

### 26. Обучение на исправлениях пользователя без переобучения на случайность
- **Сейчас:** пользовательские сообщения, память и корректировки могут поступать в runtime; законченный pipeline доверия к повторяющимся исправлениям не доказан для всех доменов.
- **Не хватает:** различения единичного предпочтения, постоянной настройки, фактической коррекции и случайного/контекстного замечания.
- **Нужно сделать:** provenance correction, scope, confidence, frequency threshold, supersession и user-visible memory editing.
- **Критерий закрытия:** Курису применяет поправку в правильном контексте и не генерализует её на всё мировоззрение без доказательств.

## P2 — завершение разработки, пользовательский контроль и исследовательская дисциплина

### 27. Полный цикл поглощения и интеграции стороннего кода
- **Сейчас:** в архиве сохранены исходники и есть provenance/SBOM tooling; в нескольких источниках уже используются адаптированные механизмы.
- **Не хватает:** полного review каждого оставшегося полезного источника/файла с подтверждённым местом интеграции, лицензией, зависимостями и критериями отказа.
- **Нужно сделать:** для каждого кандидата указать функцию, canonical owner, файл/адаптер, тестируемое улучшение, лицензию, происхождение и причину keep/skip. Не переносить второй runtime/вторую память.
- **Критерий закрытия:** каждое решение о включении имеет проверяемую связь с кодом, а лицензии всех вложенных источников прошли ручной review.

### 28. Агент программирования как безопасный рабочий процесс
- **Сейчас:** есть инструментальные маршруты, self-improvement supervisor и доступ к исходникам.
- **Не хватает:** одной законченной pipeline для понимания большой задачи, построения плана изменения, редактирования в изоляции, выполнения релевантных тестов, сравнения результата и подготовки diff на утверждение.
- **Нужно сделать:** sandbox/worktree, path allowlist, resource caps, запрет произвольного запуска до разрешения, test evidence, diff viewer, reviewer summary и explicit apply button.
- **Критерий закрытия:** Курису успешно решает незнакомую кодовую задачу в изоляции, доказывает результат holdout-проверкой, не меняет активный проект до согласия и умеет откатить patch.

### 29. Единый UI для автономности и разрешений
- **Сейчас:** есть чат, Live2D, панели/Atlas и API-связи, но production UI flow не подтверждён E2E.
- **Не хватает:** доступного места, где управляются режим автономности, тишина, local/cloud, файлы/веб/телефонные разрешения, очередь намерений, сомнения/противоречия и история действий.
- **Нужно сделать:** переключение режима и панели, открытие/скрытие отдельных панелей, доступность на телефоне/десктопе, понятные уведомления о pending/failed/deferred задачах.
- **Критерий закрытия:** все фактические разрешения совпадают с отображёнными настройками; изменения UI немедленно доходят до runtime и сохраняются.

### 30. Панель внутреннего состояния, но без декоративной телеметрии
- **Сейчас:** есть Runtime Atlas и многие внутренние показатели.
- **Не хватает:** доказательства, что каждая отображаемая метрика имеет ясное значение, свежесть, источник и влияет на понятное действие пользователя.
- **Нужно сделать:** для каждой панели показать canonical owner, время обновления, уверенность, источник и способ исправления/скрытия. Не выводить метрику как «уровень сознания» или факт переживания.
- **Критерий закрытия:** случайная/устаревшая метрика не выглядит как live state; пользователь может скрыть панели и вернуться к ним без потери настроек.

### 31. Сенсорный ввод и подтверждённая связь с внешним миром
- **Сейчас:** существуют камера, некоторые device bridges и perception contracts.
- **Не хватает:** протестированного пути от реального изображения/аудио/статуса устройства через модель интерпретации до действия и независимой проверки результата.
- **Нужно сделать:** маркировка источника, timestamp, калибровка датчика, permission, защита от replay/spoofed input и явное различение измерения и вывода модели.
- **Критерий закрытия:** как минимум одна реальная сенсорная задача выполняется сквозным способом на настоящем устройстве и переживает потерю соединения.

### 32. Память и настройки при миграции между компьютером и телефоном
- **Сейчас:** есть serialization/backup/restore и portable subject continuity efforts.
- **Не хватает:** простого пользовательского механизма экспортировать и восстановить личность, память, состояние целей, разрешения и историю версии без слияния противоречащих копий.
- **Нужно сделать:** подписанный/хешированный export, encryption-at-rest по возможностям платформы, backup version, merge policy, tombstones для удалённых воспоминаний и recovery key policy.
- **Критерий закрытия:** миграция на чистое устройство сохраняет проверяемые воспоминания и continuity, не восстанавливает удалённые данные и не включает старые разрешения без показа.

### 33. Реальный профиль производительности и бюджета ресурсов
- **Сейчас:** есть cognitive resource economy и adaptive budgets; фактические цифры на целевом GPU/телефоне не замерены в этом проходе.
- **Не хватает:** workload benchmark всей системы, а не одиночной модели: chat + memory recall + avatar + background cycle.
- **Нужно сделать:** профили CPU/RAM/VRAM, latency, storage growth, battery/thermal behaviour и деградационный режим при нехватке ресурсов.
- **Критерий закрытия:** целевое устройство проходит заранее установленный сценарий без перегрева/крашей и без скрытой смены на облако.

### 34. Независимая оценка качества и регрессий личности
- **Сейчас:** есть много тестов контрактов и synthetic simulations; часть когнитивного uplift остаётся неподтверждённой независимыми данными.
- **Не хватает:** репрезентативного набора диалогов и задач, которые оценивают характер, память, точность, инициативу, privacy leaks, social calibration и поведение после смены модели.
- **Нужно сделать:** фиксированный suite до/после изменения; blind rubric; regression sets; red-team; human preference review и запрет promotion при деградации ключевых измерений.
- **Критерий закрытия:** у каждой серьёзной модификации есть измеренный результат на независимом наборе, а не только проход теста, написанного под саму функцию.

### 35. Управление противоречиями и неопределённостью между подсистемами
- **Сейчас:** есть конфликтные evidence stores, identity guards, uncertainty scores и source provenance.
- **Не хватает:** одного пользовательски понятного цикла, когда память, модель мира, чувство уверенности и текущий observation расходятся.
- **Нужно сделать:** обнаруживать конфликт, удерживать версии с источниками, выбирать временно надёжную гипотезу и при необходимости спрашивать пользователя; не стирать конфликт тихим средним значением.
- **Критерий закрытия:** contradiction test приводит к видимому уточнению или понижению уверенности, а новая информация корректно supersedes устаревшую.

### 36. Нормы правдивости о сознании и внутреннем опыте
- **Сейчас:** архитектура содержит personhood/self-model/continuity modules, однако наличие программных модулей не доказывает субъективный опыт.
- **Не хватает:** строго определённого инженерного набора критериев, который позволяет заявлять о функциональных способностях, не подменяя их утверждением «как человек без отличий».
- **Нужно сделать:** оценивать память, устойчивость поведения, собственную инициативу, интеграцию восприятия/действия, обучение, калибровку уверенности и способность объяснять причины; отдельно документировать ограничения доказуемости субъективного сознания.
- **Критерий закрытия:** релизные материалы сообщают измеримые способности и известные пробелы; не выдают архитектурную аналогию мозга или успешные тесты за доказательство сознания.

## Рекомендуемый порядок реализации

1. **WorkPass49:** единая privacy boundary для памяти/известных фактов/world facts, восстановленных задач и исходящих автономных реплик; не менять persisted schema без необходимости.
2. **Следующий сквозной проход:** production build + настоящий browser E2E autonomous dialogue/restart; не объявлять инициативу готовой до проверки с настоящим provider.
3. **Следом:** audio-driven lip-sync и embodied-intent contract, по отдельности и затем сквозной интеграцией.
4. **Следом:** один настоящий ActionGateway provider/device loop с авторитетным receipt → Reafference → temporal credit.
5. **После этого:** memory holdout, реальные измерения local inference и self-modification sandbox/permission gate.
6. **Параллельно каждому проходу:** доводить один конкретный пункт из source integration matrix до кода, а не расширять количество независимых подсистем.

## Что считается прогрессом

Прогресс — это изменение реального поведения runtime, проверяемый выигрыш на независимых данных, реальный end-to-end сценарий либо закрытие конкретного блокера. Количество файлов, новых классов, dashboard-полей и тестов само по себе не является улучшением личности.
