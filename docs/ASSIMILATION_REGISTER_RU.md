# Реестр ассимиляции внешних источников в NK1

**Дата:** 26 ноября 2026
**Основной проект:** `runtime/neuro-kurisu` (TS-организм, 751 файл исходников)
**Источники:** `research/` и `integrations/` в этом же репозитории
**Статус документа:** живой реестр; обновляется в каждой волне ассимиляции.

## 0. Зачем этот реестр

В репозитории лежат пять независимых исследовательских кодовых баз, написанных на Python, и одна интеграция на JS. До этой волны **ни один** из них не был подключён к основному runtime: `grep` по `src/` не находил ни `nomega`, ни `omestro`, ни `deepcode`, ни `neurocore-v143`, ни `inspect-ai`. То есть это был архив, а не источник.

Реестр фиксирует по каждому источнику: что взято, куда именно встроено, чем проверено, какая ожидается польза, что осталось. Правило: **идея без теста и без точки вызова не считается ассимилированной**.

### 2.2. Как это встроено

- **Владелец состояния.** `MemoryWritePolicy` добавлен в `MemorySubsystemRuntime` рядом с `MemoryRetentionEconomy` и `MemoryCausalEconomy`. Это не второй memory store: политика ничего не хранит из памяти организма, только собственную статистику решений.
- **Срез состояния.** `persisted.system.memoryWritePolicy` — по тому же шаблону, что `memoryRetentionEconomy`: объявление в `OrganismCore`, default, `restore()` в `init`, проекция в `PersistenceProjectionCoordinator`, пропуск в `StateMigrations`.
- **Точка вызова.** В цикле кодирования памяти (`OrganismCore`, участок `memoryRetentionEconomy.assess`) политика вызывается до оценки удержания, а `observeOutcome` — после, вместе с `memoryRetentionEconomy.observeOutcome`.
- **Режимы.**
  - `shadow` (по умолчанию) — решения записываются, поведение не меняется;
  - `active` (`NEURO_MEMORY_WRITE_POLICY=active`) — гейн применяется к входной `salience01` (в пределах 0.75–1.25), а стабильная «остывшая» память может не уходить в dormant;
  - `off` — политика не считает и не растёт.
- **Наблюдаемость.** `GET /api/organism/memory/write-policy` (read-only, требует токен) отдаёт режим, число решений, средний гейн, число смен режима ошибки, число promotions, диагностику всех четырёх подмодулей и последние решения.

### 2.5. Честные ограничения волны 1

- `active`-режим проверен на коротком прогоне (6 шагов) и на юнит-уровне; долгосрочного A/B «shadow vs active» по качеству памяти **нет** — это отдельный эксперимент (волна 2).
- `promote` в runtime срабатывает редко: он требует ≥8 наблюдений одного и того же `memoryId` и флага `dormant`. В юнит-тесте сценарий воспроизведён, в runtime-прогоне promotions = 0.
- `DeepWorkSelector` в волне 1 используется с батчем из одного кандидата; его реальная ценность раскрывается на батче (replay-события, кандидаты реранка) — это волна 2.
- Перенос сетей (RSSM, C51, Option-Critic) не делался и не планируется без отдельного решения: в runtime нет тензорного слоя, и «нейронная копия» без обучения была бы декоративной.

### 2.6. A/B «shadow vs active»: что показал эксперимент

Тест `tests/memory-write-policy-ab.mjs` (24 шага, идентичные входы, три прогона: shadow, shadow, active):

| Метрика | shadow | active |
|---|---:|---:|
| Оценок удержания | 24 | 24 |
| retained / dormant / discard | 24 / 0 / 0 | 24 / 0 / 0 |
| Средний score | 0,7967 | 0,7970 |
| Средний гейн записи | 1,0066 | 1,0066 |

Дополнительный прогон с давлением (40 шагов, минимальная значимость входов, повторяющийся текст):

| Метрика | shadow | active |
|---|---:|---:|
| retained / dormant / discard | 40 / 0 / 0 | 40 / 0 / 0 |
| Средний score | 0,6713 | 0,6859 |
| Байт памяти / бюджет | 349 KB / 389 KB (90 %) | — |
| Оценок под давлением бюджета | 27 | — |

Выводы, которые важнее самих цифр:

1. **Политика работает, но в текущем режиме удержания у неё нет рычага.** Ветка `dormant`/`discard` не достигается даже при минимальной значимости входов: 40 из 40 записей получили `retain`, средний score 0,67 при пороге dormancy ниже. Гейн 0,75–1,25 сдвигает score на ±1,5 %, чего недостаточно, чтобы пересечь порог.
2. **Реальное давление — байтовый бюджет, а не score.** При 90 % бюджета 27 оценок шли с `budgetPressure01 > 0,7`, но `MemoryRetentionEconomy` только *считает* кандидатов на вытеснение (`budgetEvictionCandidates`), а фактическое вытеснение выполняет `MemoryOS2` (`budgetEvictions`). Значит, точка приложения политики для реальной экономии памяти — ранжирование при вытеснении по бюджету, а не dormancy.
3. **Runtime не бит-воспроизводим между прогонами.** Два shadow-прогона совпали по счётчикам, но средний score разошёлся на 0,0002 из-за признаков, производных от wall-clock. Поэтому A/B допустим только как агрегатный с допуском (тест это и проверяет: `< 0,02`).
4. **Побочный результат аудита:** путь dormancy в экономике удержания фактически недостижим на нормальной нагрузке, то есть память растёт монотонно и ограничивается только байтовым бюджетом p70. Это стоит проверить отдельно: либо пороги dormancy завышены, либо ветка мертва.

### 2.7. Волна 1.5: рычаг перенесён на вытеснение по бюджету

Раздел 2.6 показал, что dormancy — не та точка, где решается судьба памяти. Поэтому следующий шаг сделан сразу: политика получила вес для ранжирования при вытеснении по байтовому бюджету.

- `MemoryOS2.enforceByteBudget` принимает необязательный `valueAdjustment(m)`; множитель плотности ограничен `[0,5, 1,5]`, поэтому вызывающий может сдвинуть порядок вытеснения, но не «спасти» или «убить» память против её собственной ценности. Без хука поведение побитово прежнее.
- `MemoryFabric.maintain` пробрасывает `valueAdjustment` (опционально), `OrganismCore` передаёт его только когда режим политики не `off`.
- `MemoryWritePolicy.evictionWeight01(id)`: `0,85 + 0,35·quality − 0,15·lastUpdate`, где `quality = 0,5·reliability + 0,5·(1−lastError)`; границы `[0,85, 1,2]`. Меньше трёх наблюдений — ровно 1 (нет информации). `shadow` считает `evictionShadowWouldAdjust`, но возвращает 1; `active` применяет вес и считает `evictionAdjusted`.
- Вес масштабируется по объёму доказательств: одна запись в истории даёт треть эффекта, три и больше — полный. Без масштабирования было бы два плохих варианта: игнорировать единственное наблюдение (вес всегда 1, рычага нет) или применять полный эффект по одному наблюдению. Важно и то, что равномерный множитель для всех записей порядок вытеснения не меняет вообще — вес обязан различаться между записями.
- Проверка (`tests/memory-write-policy-eviction.mjs`): два одинаковых набора по 60 записей и одинаковый бюджет. В контроле вытесняется 19 записей по штатному порядку; с хуком первой вытесняется понижённая запись (`m-59`), защищённая (`m-0`) выживает; веса `NaN`/`1e9`/`0` зажимаются, порядок не ломается.

**Замер под давлением** (`npm run test:memory-write-policy-eviction-pressure`, 120 шагов):

| Прогон | Выживших (shadow → active) | Байт (shadow → active) | Вытеснений | Confidence выживших | Срабатываний веса |
|---|---|---|---:|---|---|
| 1 | 73 → 72 | 482,8 → 475,3 KB | 289 → 290 | 0,7842 → 0,7793 | 7 339 → 5 826 |
| 2 | 67 → 68 | 461,4 → 474,0 KB | 295 → 294 | 0,7796 → 0,7782 | 4 878 → 6 760 |

Честное чтение: **эффект по байтам нестабилен между прогонами** (в первом −7,5 KB, во втором +12,6 KB), качество выживших меняется в пределах 0,5 п.п. Единственный устойчивый факт — вес действительно срабатывает (5,8–7,3 тыс. применений за 120 шагов). Заявлять улучшение нельзя; хук остаётся ограниченным регулятором, польза которого не доказана.

**Найденная по ходу ошибка (важная).** Первый замер давал `adjusted = 0`: вес не срабатывал вообще, потому что гейт требовал ≥3 наблюдений, а у записи их одно. После масштабирования по доказательствам вес включился, но реальный `tsc` в CI показал `TS2554` на `clamp(x, .5, 1.5)`: модульный `clamp` в `MemoryOS2` нормализует к `0..1`, поэтому все защитные веса (>1) молча становились 1 и работала только понижающая часть. Ошибку не видел локальный «degraded» typecheck (только strip-синтаксис) — её поймал CI, который ставит pinned TypeScript из app-локфайла. Исправлено локальной границей `Math.max(.5, Math.min(1.5, x))`; после этого `tsc -p tsconfig.clean.json --noEmit` даёт 0 ошибок, а замеры выше сделаны уже с исправленным кодом.

Вывод для процесса: `npm run typecheck` без установленного компилятора — это проверка синтаксиса, а не типов. Перед PR стоит ставить TypeScript (`npm ci --prefix app`) или запускать `NEURO_TYPECHECK_STRICT=1`, иначе семантические ошибки всплывают только в CI.

> **Третий прогон под давлением, уже с исправленной формулой** (`npm run test:memory-write-policy-eviction-pressure`, 120 шагов): shadow 74 выживших / 486,5 KB / 288 вытеснений, active 72 / 480,1 KB / 290 вытеснений, применений веса 6 717. То есть по байтам −6,4 KB, что в пределах разброса предыдущих прогонов (−7,5 KB и +12,6 KB). Бюджет при этом различается между прогонами (468,7 и 465,8 KB), поэтому сравнение «в байтах» шумит на ±3 KB. Вывод не меняется: как регулятор размера вес работает, но выигрыш в байтах не доказан; доказанная польза — в 2.11, где измеряется не размер, а качество удержанного.

> **Поправка после 2.11.** Формула веса исправлена: было `quality = 0.5·reliability + 0.5·(1−error)`, из-за чего при здоровом канале шумная запись получала вес **выше** 1 и защищалась. Стало `quality = 0.7·(1−error) + 0.3·reliability`, `target = clamp(1 + 0.4·(quality − 0.5) − 0.15·update, 0.85, 1.2)` — свидетельство самой записи доминирует, канал только модулирует. Замеры в 2.6–2.10 сделаны на старой формуле; после исправления вес сильной записи 1,12 → 1,14, шумной — 0,91.

### 2.10. Замер полезности: защищаем ли мы то, что реально используется (предварительный, заменён разделом 2.11)

Вопрос, который остался открытым после замера под давлением: вес вытеснения меняет состав памяти, но полезно ли это. Метрика простая — сколько раз выжившие записи реально запрашивались (`retrievalCount`), и сколько байт тратится на одно использование.

`npm run test:memory-write-policy-retrieval-hit` (150 шагов, shadow → active, одинаковые входы):

| Метрика | shadow | active |
|---|---:|---:|
| Выживших записей | 70 | 68 |
| Байт памяти (бюджет 460 KB) | 472,7 KB | 477,1 KB |
| Суммарные retrieval по выжившим | 73 | 62 |
| Доля выживших, которые использовались | 21,4 % | 23,5 % |
| Байт на одно использование | 6 476 | 7 695 |
| Подкреплений политики | 590 | 590 |
| Срабатываний веса | 5 432 (would) | 13 019 (applied) |

Честное чтение: доля используемых записей чуть выше в `active` (23,5 % против 21,4 %), но суммарных использований меньше (62 против 73) и байт на использование больше. Это **один прогон**, и направление снова не даёт права утверждать пользу: защита памяти пока не доказанно увеличивает её использование. Вывод для волны 2: нужен holdout-корпус с известными запросами и несколькими seed'ами, иначе метрика измеряет шум рантайма (часть признаков зависит от wall-clock).

Что при этом стало явно лучше и измеримо: подкрепления (590 за 150 шагов) реально доходят до политики, и вес наконец работает в полную силу — раньше он видел одно наблюдение и работал в треть силы.

### 2.9. Волна 1.6: политика подключена к свидетельствам использования

Симптом: `decide()` видел каждую память ровно один раз, в момент записи. Значит история на память = 1 наблюдение, гейт стабильности (`minimumUpdates = 8`) недостижим, а вес вытеснения работал максимум в треть силы. Политика была подключена к записи, но не к тому, что происходит с памятью дальше.

Что сделано:

- `MemoryWritePolicy.observeReinforcement()` — вызывается при каждом retrieval (не более 4 записей за шаг) и обновляет историю памяти (`observations`, `lastSalience`, `lastUpdate`), не трогая канал ошибок: retrieval — это не ошибка предсказания, а факт использования.
- `MemoryWritePolicy.planDeepWork()` — прогоняет **реальный** батч кандидатов консолидации через `DeepWorkSelector` вместо батча из одного элемента, который видит `decide()`. Пока только замер: размер батча по-прежнему выбирает runtime.
- Счётчики (`reinforcements`, `promoteEligible`, `deepWorkBatch`) живут в снапшоте и восстановлении, видны в `GET /api/organism/memory/write-policy`.

Результат замера (12 циклов + юнит-проверки):

| Метрика | Было | Стало |
|---|---:|---:|
| Наблюдений на память | 1 (только запись) | 2–9 (запись + retrieval) |
| Вес защищённой памяти | до 1,04 (треть силы) | до 1,12 (полная сила) |
| `promoteEligible` в живом цикле | недостижим | 0 |

Честно: подкрепления работают, но **промоушен всё равно не срабатывает** — в живом цикле ошибка предсказания ≈0,35, а гейт требует ≤0,2. То есть dormancy-возврат остаётся мёртвой ветвью при текущем качестве предсказания, и это ограничение данных, а не кода.

Находка и исправление по `DeepWorkSelector`: на реальном батче из 4 кандидатов селектор сначала выбирал 3 (75 %), причём причина в большинстве проходов — `capped-at-maximum`. Абсолютный порог 0,22 при наблюдаемых ошибках 0,35–0,5 относит к «глубокой» ветке почти всех, то есть селектор не различал кандидатов.

Добавлен относительный режим (`relativeToBatch`): порог считается по медиане самого батча, сравнение строгое, а границы доли (5–95 %) остаются в силе. Батч без внутренних различий не уходит в дорогую ветку целиком — он падает на минимальную долю (1 из 4). В политике относительный режим включён только для батчевого маршрута; одиночный вызов из `decide()` сохраняет прежнюю семантику.

После перекалибровки: 22 из 44 кандидатов (50 %), причина стабильно `relative-threshold` — селектор наконец разделяет батч. Экономии это ещё не доказывает: нужен замер стоимости глубокой ветки.

Тест: `tests/memory-write-policy-reinforcement.mjs` — входит в `npm run test:assimilation-wave1`.

### 2.11. Политика проверена штатным инструментом: канонический retrieval-benchmark

Самодельная метрика из 2.10 дублировала то, что в проекте уже есть: `MemoryRetrievalBenchmark` (686 строк) владеет честной оценкой памяти — holdout-сплит, проверка утечки train/holdout по 3-граммным шинглам, bootstrap-доверительные интервалы, HMAC-подпись свидетельства, явный контракт `promotion`. Поэтому A/B политики перенесён на него, а не остался на счётчиках.

`tests/memory-write-policy-retrieval-benchmark-ab.mjs`:

- оба плеча стартуют с **одного** снапшота и режутся **одним** байтовым бюджетом; различается только правило удержания (`valueAdjustment` из политики или отсутствие правила);
- бюджет выводится из объёма «шумовых» записей, чтобы давление обязано было выбирать между шумом и размеченными записями, а не удалять бесконечный дешёвый шум;
- фикстура «равных значимостей»: значимость и размер одинаковые, различаются только свидетельства — это вопрос «добавляет ли информация политики ценность там, где базовый ранжировщик слеп»;
- фикстура «разрыва значимости»: шум с `salience 0.95` — проверка, что ограниченный вес **не** переворачивает важность.

Результат (равные значимости):

| Метрика | control | treatment |
|---|---:|---:|
| Вытеснено записей | 30 | 29 |
| Сильные (8) выжили | 5 | **8** |
| Слабые (8) выжили | 0 | **8** |
| `recall@5` (канонический отчёт) | 0,417 | **1,0** |
| `MRR` | 0,417 | **1,0** |
| Меток без записи в корпусе | 7 | 0 |

Веса: сильная запись 1,13, шумовая 0,914.

Сценарий с разрывом значимости: treatment сохраняет 4 из 8 сильных, control — 0 из 8. То есть вес помогает, но важность не переворачивает — и это закреплено утверждением теста, а не оговоркой в тексте.

Контракт инструмента соблюдён: `promotion.allowed = false` (синтетический фикстур никогда не даёт права на промоушен), `guardrails.liveMemoryMutated = false`, `datasetIntegrity.unknownRelevantMemoryIdCount = 0` в treatment. В control он равен 7: инструмент сам сообщает, что часть меток потеряна вместе с записями, вместо того чтобы молча считать recall по выжившим.

Честная граница вывода: это доказывает, что механизм работает **когда свидетельства информативны**, и что он ограничен по силе. Это не доказывает, что в реальном рантайме свидетельства информативны — для этого нужен настоящий корпус с независимой разметкой.

### 2.12. Целостность забывания: запись не воскресает

`forgetById` — единственная операция, которая обещает, что памяти нет. Остаточный производный индекс, обратная ссылка или строка в снапшоте дают «воскрешение» после рестарта, которого снаружи не видно.

`tests/memory-forget-integrity.mjs` проверяет на живом `MemoryOS2`:

- до забывания запись находится по уникальному токену;
- `forgetById` возвращает `true` один раз, повторный вызов и забывание неизвестного id — `false`;
- канонический store, `statsLight().items` и байтовый учёт уменьшаются ровно на одну запись, `memoryAccountingDiagnostics().exact = true` (не приблизительно);
- retrieval больше не возвращает запись;
- ни одна другая запись не держит ссылку на забытую в `semantic/temporal/causal/contradictionLinks` (иначе графовый retrieval её раскрывает);
- после `restore` снапшота запись не воскресает, а соседи по теме живы — забывание не заразно.

Замер: 5 записей / 2052 байта → 4 записи / 1617 байт, попаданий в retrieval 1 → 0, учёт точный.

### 2.13. Гейт отвечаемости не умел отказывать на чужом коде

Билингвальный корпус (раздел 2.14) сразу нашёл дефект: запрос «пломба гидроцилиндра КХ-ПЛОМБА-0 лебёдка» возвращал `ru-note-0`, `abstained=false`, `correctAbstentionRate01=0`, `unsupportedRetrievalRate01=1`. То есть на вопрос, которого в памяти нет, система уверенно отдавала постороннюю запись.

Причина — три слоя, каждый по отдельности безобидный:

1. `identifierPattern` был ASCII-only (`[A-Z]{2,}[-_/]?[0-9]{2,}`), а `normalizeIdentifier` вырезал всё, кроме `A-Z0-9`, поэтому `КХ-РУ-0` нормализовался в `0`: кириллические коды вообще не считались идентификаторами.
2. Без распознанного идентификатора фрагменты кода попадали в обычные токены (`кх`, `0`), и `coverage` достигал 0,40 при пороге 0,30 — этого хватало, чтобы «слабое» свидетельство обосновало случайную запись.
3. В JS `\b` и `\w` остаются ASCII даже с флагом `u`, поэтому просто добавить `\p{L}` в старый паттерн было недостаточно: границы слова для кириллицы не срабатывали.

Исправление (`MemoryOS2.ts`):

- паттерн идентификатора работает в любой письменности и использует lookbehind/lookahead по `\p{L}\p{N}` вместо `\b`;
- нормализация сохраняет буквы любого алфавита и цифры;
- новый флаг `identifierConflict`: если в запросе есть код, а в записи есть другой код, «слабые» свидетельства (coverage, fuzzy, entity, metadata, concept) больше не обосновывают выдачу. Точная фраза и морфология остаются — они требуют реального совпадения текста.

Замер на билингвальном корпусе, до → после:

| Метрика (кандидат) | до | после |
|---|---:|---:|
| recall@5 | 1,0 | 1,0 |
| MRR | 0,9063 (en 0,8125) | **1,0** |
| корректный отказ | 0 | **1,0** |
| неподдержанные выдачи | 1,0 | **0** |

MRR вырос не из-за «подкрутки» ранжирования: ложное попадание по чужому коду стояло выше правильной записи и исчезло. Регрессии: 16 тестов retrieval/abstention (включая `memory-retrieval-grounded-abstention-workpass574` и `memory-retrieval-fuzzy-workpass32`) и 12 тестов памяти — PASS, `tsc` 0 ошибок.

### 2.14. Билингвальный корпус и свидетельства из реальных прогонов

Канонический инструмент требовал того, чего в репозитории не было: ≥2 train-запроса, ≥8 answerable и ≥2 unanswerable holdout-запроса **на каждый язык**, каждая holdout-строка в своей independence-группе, без пересечения запросов между сплитами. Появились:

| Файл | Что делает |
|---|---|
| `tests/fixtures/memory-retrieval-bilingual-corpus.mjs` | 20 размеченных записей (10 ru + 10 en), 40 отвлекающих, 28 запросов: 4 train + 8 answerable holdout + 2 unanswerable на язык; у каждой holdout-строки своя группа; provenance с `contentSha256` |
| `tests/memory-retrieval-bilingual-corpus.mjs` | проверяет языковой контракт (минимумы по каждому языку), отсутствие утечки train/holdout, дубликатов запросов и неизвестных меток, нулевые quarantined/stale/dormant/future-выдачи |
| `tests/memory-write-policy-derived-evidence.mjs` | свидетельства политики выводятся из реальных операционных запросов, а не впрыскиваются руками |

**Честный итог по корпусу.** Кандидат (MemoryOS2) не обгоняет BM25 на корпусе уникальных кодов: после исправления оба дают recall@5 = 1,0 и MRR = 1,0, `deltas = 0`, `promotion.allowed = false`, `promotionStatus = not-promoted`. Гейт промоушена по праву отказывает: на задаче «найди запись по коду» лексический базлайн уже идеален, и заявлять победу нечем. Ценность корпуса не в победе, а в том, что он ловит дефекты (раздел 2.13) и не даёт выдать однопроцентный шум за улучшение.

**Свидетельства из эксплуатации.** Раньше A/B впрыскивал «сильный/шумный» профиль вручную. Теперь 20 операционных запросов «код КХ-РУ-i» / «code KX-EN-i» проходят через настоящий retrieval, результат каждого попадания пишется в политику (`observeOutcome`), holdout-метки при этом не используются вовсе.

Первый прогон дал ровно ноль эффекта (3 из 16 выживших размеченных записей в обоих плечах). Причина оказалась дефектом, а не «пределом веса»: у записи без истории `lastUpdate01 = |0,85 − 0| = 0,85`, и штраф `0,15 · 0,85 = 0,1275` гасил ровно ту защиту (`+0,118`), которую приносило это же первое наблюдение. Первое наблюдение — не «дрожание»: сравнивать не с чем. Введён `MemoryWritePolicy.salienceUpdate01`, который считает изменение только между двумя реальными замерами.

Замер после исправления (бюджет 21 787 Б, вытеснено по 23 записи в обоих плечах):

| Метрика | контроль | treatment |
|---|---:|---:|
| выжило размеченных из 16 | 3 | **7** |
| recall@5 | 0,1875 | **0,4375** |
| MRR | 0,1875 | **0,4375** |
| неизвестных меток | 13 | **9** |
| вес использованной / неиспользованной записи | 1 / 1 | 1,0432 / 1 |

Ограничение, которое надо называть вслух: в фикстуре операционный запрос совпадает с меткой (код = метка), поэтому измерена **конверсия** «информативное свидетельство → лучшее удержание», а не информативность реального трафика. Отрицательных сигналов в этом сценарии нет вообще: гейт отвечаемости отдаёт только обоснованные строки, поэтому «пользователь проигнорировал хвост» не возникает. Это сообщается в выводе теста, но не превращается в утверждение.

## 4. Правила ассимиляции (чтобы не размножать владельцев)

1. Один владелец на тип состояния. Политика — владелец своей статистики; память остаётся у `MemoryFabric`/`MemoryOS2`.
2. Новый механизм входит в `shadow`-режиме, включается флагом, и только потом обсуждается `active` по умолчанию.
3. Каждый перенос обязан иметь: юнит-тест на семантику источника, интеграционный тест на точку вызова и запись в этом реестре.
4. Ограничения источника сохраняются: если в Python модуль «candidate-only, disabled by default», в NK1 он тоже не включён по умолчанию.
5. Если перенос требует тензорного слоя, переносится политика (числа, пороги, правила), а не сеть.
