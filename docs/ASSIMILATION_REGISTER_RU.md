# Реестр ассимиляции внешних источников в NK1

**Дата:** 26 ноября 2026
**Основной проект:** `runtime/neuro-kurisu` (TS-организм, 751 файл исходников)
**Источники:** `research/` и `integrations/` в этом же репозитории
**Статус документа:** живой реестр; обновляется в каждой волне ассимиляции.

## 0. Зачем этот реестр

В репозитории лежат пять независимых исследовательских кодовых баз, написанных на Python, и одна интеграция на JS. До этой волны **ни один** из них не был подключён к основному runtime: `grep` по `src/` не находил ни `nomega`, ни `omestro`, ни `deepcode`, ни `neurocore-v143`, ни `inspect-ai`. То есть это был архив, а не источник.

Реестр фиксирует по каждому источнику: что взято, куда именно встроено, чем проверено, какая ожидается польза, что осталось. Правило: **идея без теста и без точки вызова не считается ассимилированной**.

### 2.2. Как это встроено

- **Владелец состояния.** `MemoryWritePolicy` добавлен в `MemorySubsystemRuntime` рядом с `MemoryRetentionEconomy` и `MemoryCausalEconomy`. Это не второй memory store: политика ничего не хранит из памяти организма, только собственную статистику решений.
- **Срез состояния.** `persisted.system.memoryWritePolicy` — по тому же шаблону, что `memoryRetentionEconomy`: объявление в `OrganismCore`, default, `restore()` в `init`, проекция в `PersistenceProjectionCoordinator`, пропуск в `StateMigrations`.
- **Точка вызова.** В цикле кодирования памяти (`OrganismCore`, участок `memoryRetentionEconomy.assess`) политика вызывается до оценки удержания, а `observeOutcome` — после, вместе с `memoryRetentionEconomy.observeOutcome`.
- **Режимы.**
  - `shadow` (по умолчанию) — решения записываются, поведение не меняется;
  - `active` (`NEURO_MEMORY_WRITE_POLICY=active`) — гейн применяется к входной `salience01` (в пределах 0.75–1.25), а стабильная «остывшая» память может не уходить в dormant;
  - `off` — политика не считает и не растёт.
- **Наблюдаемость.** `GET /api/organism/memory/write-policy` (read-only, требует токен) отдаёт режим, число решений, средний гейн, число смен режима ошибки, число promotions, диагностику всех четырёх подмодулей и последние решения.

### 2.5. Честные ограничения волны 1

- `active`-режим проверен на коротком прогоне (6 шагов) и на юнит-уровне; долгосрочного A/B «shadow vs active» по качеству памяти **нет** — это отдельный эксперимент (волна 2).
- `promote` в runtime срабатывает редко: он требует ≥8 наблюдений одного и того же `memoryId` и флага `dormant`. В юнит-тесте сценарий воспроизведён, в runtime-прогоне promotions = 0.
- `DeepWorkSelector` в волне 1 используется с батчем из одного кандидата; его реальная ценность раскрывается на батче (replay-события, кандидаты реранка) — это волна 2.
- Перенос сетей (RSSM, C51, Option-Critic) не делался и не планируется без отдельного решения: в runtime нет тензорного слоя, и «нейронная копия» без обучения была бы декоративной.

### 2.6. A/B «shadow vs active»: что показал эксперимент

Тест `tests/memory-write-policy-ab.mjs` (24 шага, идентичные входы, три прогона: shadow, shadow, active):

| Метрика | shadow | active |
|---|---:|---:|
| Оценок удержания | 24 | 24 |
| retained / dormant / discard | 24 / 0 / 0 | 24 / 0 / 0 |
| Средний score | 0,7967 | 0,7970 |
| Средний гейн записи | 1,0066 | 1,0066 |

Дополнительный прогон с давлением (40 шагов, минимальная значимость входов, повторяющийся текст):

| Метрика | shadow | active |
|---|---:|---:|
| retained / dormant / discard | 40 / 0 / 0 | 40 / 0 / 0 |
| Средний score | 0,6713 | 0,6859 |
| Байт памяти / бюджет | 349 KB / 389 KB (90 %) | — |
| Оценок под давлением бюджета | 27 | — |

Выводы, которые важнее самих цифр:

1. **Политика работает, но в текущем режиме удержания у неё нет рычага.** Ветка `dormant`/`discard` не достигается даже при минимальной значимости входов: 40 из 40 записей получили `retain`, средний score 0,67 при пороге dormancy ниже. Гейн 0,75–1,25 сдвигает score на ±1,5 %, чего недостаточно, чтобы пересечь порог.
2. **Реальное давление — байтовый бюджет, а не score.** При 90 % бюджета 27 оценок шли с `budgetPressure01 > 0,7`, но `MemoryRetentionEconomy` только *считает* кандидатов на вытеснение (`budgetEvictionCandidates`), а фактическое вытеснение выполняет `MemoryOS2` (`budgetEvictions`). Значит, точка приложения политики для реальной экономии памяти — ранжирование при вытеснении по бюджету, а не dormancy.
3. **Runtime не бит-воспроизводим между прогонами.** Два shadow-прогона совпали по счётчикам, но средний score разошёлся на 0,0002 из-за признаков, производных от wall-clock. Поэтому A/B допустим только как агрегатный с допуском (тест это и проверяет: `< 0,02`).
4. **Побочный результат аудита:** путь dormancy в экономике удержания фактически недостижим на нормальной нагрузке, то есть память растёт монотонно и ограничивается только байтовым бюджетом p70. Это стоит проверить отдельно: либо пороги dormancy завышены, либо ветка мертва.

### 2.7. Волна 1.5: рычаг перенесён на вытеснение по бюджету

Раздел 2.6 показал, что dormancy — не та точка, где решается судьба памяти. Поэтому следующий шаг сделан сразу: политика получила вес для ранжирования при вытеснении по байтовому бюджету.

- `MemoryOS2.enforceByteBudget` принимает необязательный `valueAdjustment(m)`; множитель плотности ограничен `[0,5, 1,5]`, поэтому вызывающий может сдвинуть порядок вытеснения, но не «спасти» или «убить» память против её собственной ценности. Без хука поведение побитово прежнее.
- `MemoryFabric.maintain` пробрасывает `valueAdjustment` (опционально), `OrganismCore` передаёт его только когда режим политики не `off`.
- `MemoryWritePolicy.evictionWeight01(id)`: `0,85 + 0,35·quality − 0,15·lastUpdate`, где `quality = 0,5·reliability + 0,5·(1−lastError)`; границы `[0,85, 1,2]`. Меньше трёх наблюдений — ровно 1 (нет информации). `shadow` считает `evictionShadowWouldAdjust`, но возвращает 1; `active` применяет вес и считает `evictionAdjusted`.
- Вес масштабируется по объёму доказательств: одна запись в истории даёт треть эффекта, три и больше — полный. Без масштабирования было бы два плохих варианта: игнорировать единственное наблюдение (вес всегда 1, рычага нет) или применять полный эффект по одному наблюдению. Важно и то, что равномерный множитель для всех записей порядок вытеснения не меняет вообще — вес обязан различаться между записями.
- Проверка (`tests/memory-write-policy-eviction.mjs`): два одинаковых набора по 60 записей и одинаковый бюджет. В контроле вытесняется 19 записей по штатному порядку; с хуком первой вытесняется понижённая запись (`m-59`), защищённая (`m-0`) выживает; веса `NaN`/`1e9`/`0` зажимаются, порядок не ломается.

**Замер под давлением** (`npm run test:memory-write-policy-eviction-pressure`, 120 шагов, два независимых прогона):

| Метрика | shadow | active |
|---|---:|---:|
| Выживших записей | 67 / 69 | 72 / 73 |
| Байт памяти (бюджет 461–464 KB) | 479,0 / 482,9 KB | 476,9 / 479,9 KB |
| Вытеснений | 295 / 293 | 290 / 289 |
| Средняя confidence выживших | 0,7704 / 0,7743 | 0,7826 / 0,7855 |
| Средняя salience выживших | 0,3754 / 0,3685 | 0,3651 / 0,3619 |
| Средняя ошибка предсказания | 0,3591 / 0,3557 | 0,3592 / 0,3547 |
| Срабатываний веса | 6 344–7 317 (would) | 5 827–7 050 (applied) |

Честное чтение: направление устойчиво в двух прогонах — `active` удерживает на 4–5 записей больше при на 2–3 KB меньшем объёме, вытеснений меньше, средняя confidence выживших выше на 1,2–1,5 п.п. Но величина мала (5 вытеснений из ~290), а salience и authority выживших чуть ниже, поэтому заявлять «стало лучше» пока нельзя — только «эффект есть, направление стабильное, размер в пределах шума». Порог вытеснения по бюджету к тому же превышается на 3–4 % между циклами обслуживания (каждые 8 тиков) — это прежнее поведение, не следствие правки.

Дальше: длинный прогон (≥500 шагов) с несколькими seed'ами и метрикой полезности выживших (retrieval hit), иначе вывод останется на уровне направления.

## 4. Правила ассимиляции (чтобы не размножать владельцев)

1. Один владелец на тип состояния. Политика — владелец своей статистики; память остаётся у `MemoryFabric`/`MemoryOS2`.
2. Новый механизм входит в `shadow`-режиме, включается флагом, и только потом обсуждается `active` по умолчанию.
3. Каждый перенос обязан иметь: юнит-тест на семантику источника, интеграционный тест на точку вызова и запись в этом реестре.
4. Ограничения источника сохраняются: если в Python модуль «candidate-only, disabled by default», в NK1 он тоже не включён по умолчанию.
5. Если перенос требует тензорного слоя, переносится политика (числа, пороги, правила), а не сеть.
