# NK1 — план глубокой оптимизации (2026-10-24)

## Цель

Снижать задержку, потребление памяти и стоимость когнитивного цикла без ухудшения качества памяти, обучения, безопасности и автономной инициативы. Не считать уменьшение строк кода или зелёный smoke-тест доказательством ускорения.

## Что известно из текущей базы

- Рабочее дерево исходников находится в `workpass70-source`; `main` в основном хранит release-процессы и отчёты.
- README отмечает, что независимый retrieval benchmark пока показывает `recallDelta=0`. Поэтому нельзя продвигать оптимизацию поиска памяти как улучшение качества без независимого измерения.
- В репозитории уже есть специализированные команды для memory retrieval, language-context budget, integration, typecheck, asset audit и release verification. Сначала использовать существующие проверки, не создавать дублирующие системы тестирования.
- Этот проход создаёт изолированную ветку и инструменты измерения. Это не означает, что весь runtime уже профилирован или что прирост производительности доказан.

## Приоритеты оптимизации

### P0 — измеримость и воспроизводимость
1. Зафиксировать baseline на неизменяемом наборе задач: p50/p95 latency, throughput, peak RSS, размер контекста, токены/стоимость, recall@k, task success, regret, calibration, forgetting и число ошибок.
2. Сравнивать baseline и candidate на одинаковых данных, конфигурации и paired seeds; holdout не использовать для настройки.
3. Записывать commit SHA, версию среды, конфигурацию, warm/cold режим, число повторов и сырые результаты в JSONL.
4. Блокировать продвижение, если качество памяти/задач падает сверх заранее установленного допуска, даже если latency улучшается.

### P1 — когнитивный runtime
1. Профилировать Perceive → Appraise → Plan → Act → Reflect → Consolidate отдельно; измерять каждый этап, а не только общую длительность.
2. Сократить повторную сериализацию и повторное вычисление только там, где профилирование подтверждает горячую точку.
3. Добавить ограниченные TTL-кэши для чистых, версионируемых вычислений. Ключ обязан включать все семантически значимые входы/версию модели; не кэшировать изменяемые состояния, разрешения или решения EthicalGate.
4. Вводить дедупликацию конкурентных одинаковых запросов (single-flight) и отмену устаревшей работы, если это совместимо с текущими контрактами.
5. Ограничивать фоновые задачи бюджетами CPU/памяти и приоритетом; интерактивный цикл не должен ждать консолидацию памяти.

### P2 — память и обучение
1. Измерять стоимость каждого этапа retrieval: нормализация, candidate generation, reranking, provenance/permissions и synthesis.
2. Оптимизировать candidate generation только с отчётом recall/latency; ускорение при падении recall не считать улучшением.
3. Сохранять provenance, временные метки, confidence и границы доступа при индексации/кэшировании.
4. Отделять быстрый рабочий контекст от дорогой долговременной консолидации; не терять факты при сжатии.
5. Оценивать обучение по paired seeds, validation и независимому holdout; предотвращать утечку holdout и регрессии на старых навыках.

### P3 — приложение, запуск и артефакты
1. Разделить размер/время production build, startup, first response и idle footprint.
2. Проверить динамические импорты, тяжёлые зависимости и дублирование ресурсов только по реальному bundle report.
3. Проверить таймеры, подписки, event listeners и фоновые polling loops на утечки и дублирование.
4. Не менять форматы данных/миграции и не удалять старые пути до проверки совместимости с текущим release archive.
5. Для каждого изменения — отдельный commit `[NK1][optimization] ...`, CHANGELOG и проверяемый rollback.

## Гейты принятия изменения

Оптимизация принимается только при наличии:
- воспроизводимого измерения до/после и версии commit;
- отсутствия ухудшения критических тестов/контрактов;
- отсутствия регрессии task success, retrieval recall, безопасности и корректности памяти;
- явного решения: принять, отклонить или оставить экспериментальной.

Если baseline отсутствует, изменение остаётся экспериментом. Не придумывать проценты ускорения.

## Инструмент первого прохода

`node tools/optimization-scan.mjs [root]` — read-only инвентаризация размеров исходников, больших файлов и идентичных файлов по SHA-256. Она не профилирует время исполнения и не доказывает наличие дублирования логики; её результаты — подсказки для следующего адресного профилирования.

## Следующий технический цикл

1. Запустить сканер на корне проекта и отдельно на `app`, `runtime/neuro-kurisu`, `tools`.
2. Изучить крупнейшие runtime-модули и реальные call paths.
3. Выполнить существующий retrieval benchmark и language-context-budget тест; сохранить исходные результаты.
4. Выбрать одну горячую точку, внести минимальное изменение, выполнить парный benchmark и regression suite.
5. Только после подтверждения обновлять release-артефакт. Эта ветка сама по себе не изменяет опубликованный release ZIP.
