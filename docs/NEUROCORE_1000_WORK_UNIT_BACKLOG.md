# NeuroCore — 1,000-work-unit execution backlog

**Purpose:** turn the strategic plan into actionable, trackable engineering work without pretending every task is already investigated. This is a generated work breakdown, not 1,000 completed changes and not a command to implement every idea. Every row is an atomic work unit with a domain, subsystem, lifecycle stage and expected evidence. Work is executed by dependency and measured impact, not by table order alone.

**Current branch:** `workpass70-source`  
**Master strategy:** [NEUROCORE_MASTER_STRATEGY_AND_BRAIN_MAP.md](NEUROCORE_MASTER_STRATEGY_AND_BRAIN_MAP.md)  
**Canonical rules:** [NEUROCORE_START_HERE.md](../NEUROCORE_START_HERE.md), [AGENTS.md](../AGENTS.md)  
**Status semantics:** all rows below start as **PLANNED / UNVERIFIED** until the corresponding code/tests/evidence are linked in a future update.

## How to use this backlog

- This matrix expands **20 engineering domains × 10 subsystems × 5 lifecycle gates = 1000 distinct work units**.
- Each row must be linked to the owning source path, issue/commit, test and result when started. If the repository shows that a proposed sub-area has no useful implementation need, mark it **REJECTED / NOT APPLICABLE** with a reason instead of creating code to satisfy the plan.
- Do not execute all rows mechanically. Choose the highest-risk dependency first; combine rows into a pass only when they share the same canonical owner and can be tested coherently.
- No mass file generation, no thousand empty stubs, no ticket-count metric. The count is planning coverage only.
- Status values: `PLANNED`, `IN_PROGRESS`, `BLOCKED`, `PASS`, `FAIL`, `DEFERRED`, `REJECTED`. Only `PASS` requires a verifiable evidence link.
- Priority is assigned at scheduling time: P0 blocks release or risks truth/safety/privacy; P1 blocks major advertised capability; P2 improves quality/efficiency; P3 speculative research.
- A row's test/evidence requirement can be refined after inspecting source. Never invent a path or claim a subsystem exists before the live inventory confirms it.

A work unit is complete only when its status is updated and it points to: exact owner/source path; commit or diff; test command and outcome; CI run or explicitly stated local environment; raw result artifact where relevant; known limitations; and rollback/rejection reason. A passing unit test is not sufficient evidence for a scientific or product-level claim.

## Decomposition rule for further detail

If a unit still combines independent behaviors, split it by distinct state transition, failure mode, interface boundary, resource constraint, or evaluation condition. Each child needs its own acceptance criterion. Continue decomposing until an engineer can implement and test it without guessing. This creates a path to several thousand concrete work items without padding the repository with artificial task names.
