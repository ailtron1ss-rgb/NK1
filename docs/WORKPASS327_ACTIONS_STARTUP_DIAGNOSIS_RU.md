# WorkPass327 — диагностика отказов GitHub Actions до запуска runner

Дата исследования: 2026-10-23. Репозиторий: `ailtron1ss-rgb/NK1`.

## Итог на данный момент

**Подтверждённый технический симптом:** GitHub завершает свежие задания до назначения runner и до первого шага. Это не похоже на падение тестов NK1: тесты даже не начинались.

**Наиболее приоритетная гипотеза — блокировка аккаунта/доступа к Actions на стороне GitHub Billing & Licensing.** Окончательное подтверждение требует прочитать текст аннотации check run или непосредственно проверить Billing & Licensing в аккаунте. Репозиторный connector показывает, что у свежего check run есть две аннотации, но не предоставляет их тела; поэтому этот отчёт не объявляет биллинговую блокировку доказанным фактом.

### 2. Глобальный статус GitHub

Во время внешней проверки страница GitHub Status показывала Actions как Operational. Это не опровергает проблему отдельного аккаунта или остаточную ошибку, но оснований продолжать многократно перезапускать одинаковые задания нет.

### 3. Сопоставление с публичным случаем той же сигнатуры

В [GitHub Community discussion #210692 от 2026-10-20](https://github.com/orgs/community/discussions/210692) описан такой же сбой на `ubuntu-latest`: `runner_id=0`, пустое имя runner, `steps=[]`, завершение через несколько секунд и `BlobNotFound` в логах. В обсуждении приведён конкретный ответ annotation: «The job was not started because your account is locked due to a billing issue». Это относится к чужому аккаунту, поэтому использовать его как доказательство состояния NK1 нельзя; однако совпадение симптомов достаточно сильное, чтобы проверить биллинг прежде, чем менять ещё код.

### 4. Официальный порядок разблокировки

Официальная инструкция GitHub: [Unlocking a locked account](https://docs.github.com/en/billing/how-tos/troubleshooting/locked-account). Она подтверждает, что неудачная авторизация платежа может блокировать Actions даже на GitHub Free — даже если нет активной подписки, баланса или ранее удалён способ оплаты.

Путь для владельца аккаунта:

1. GitHub → аватар → **Settings** → **Billing & Licensing** → **Payment information**.
2. Проверить уведомления о declined payment, failed authorization hold, billing lock или проблеме метода оплаты.
3. Если отображается блокировка, обновить/повторно авторизовать подходящий способ оплаты согласно странице GitHub. Не нужно запускать новые тесты до снятия блокировки.
4. Если страница не показывает активной проблемы, обратиться в [GitHub Support](https://support.github.com/contact) и приложить IDs `39908251190`, `39906315773`, job ID `120265054694`, точное время и описание: `runner_id=0`, `runner_name=""`, `runner_group_id=0`, `steps=[]`, нет логов. Попросить проверить account-level Actions/billing restriction.

## Что сделано в коде и что не исправляется коммитом

- WorkPass326 обновляет workflow actions, использует единый `.nvmrc`, добавляет CI runtime audit и шесть regression checks.
- Локальная проверка нового JS-аудита на Node.js 22.16.0: 6/6 тестов прошли.
- Статическая проверка фактических двух workflow-файлов подтвердила отсутствие `checkout@v4`/`setup-node@v4`, наличие `setup-node@v7`, проверку `.nvmrc`, PR-триггер на `rebuild` и 20-минутный тайм-аут.
- GitHub Actions на текущем HEAD пока не подтверждает успешное выполнение: свежий run снова завершился до первого шага.
- Изменения в репозитории не могут разблокировать биллинг аккаунта. Не публиковать этот PR как проверенный релиз и не обновлять основной release ZIP до фактически выполненных проверок.

## Критерий завершения диагностики

Диагноз будет подтверждён, когда будет прочитан текст аннотации именно одного из собственных check runs NK1 или когда владелец аккаунта увидит/устранит блокировку в Billing & Licensing. После этого нужно запустить проверки на точном актуальном SHA; только runner с реальными шагами даст сведения о следующих ошибках кода, если они останутся.


## Последующая интеграция веток (2026-10-23)

- Интеграционная рабочая ветка уже использовала корневой `.nvmrc = 24`; в ветке CI-hardening оставался старый `22.16.0` из `rebuild`. При объединении сохранён более новый pin интеграционной ветки, чтобы не откатывать runtime.
- Проверка совместимости CI адаптирована к разрешённому формату `.nvmrc`: major pin (`24`) или точная версия (`24.0.1`). Строгая привязка к `.nvmrc` применяется к двум основным регрессионным workflow WorkPass71/79; остальные текущие workflow продолжают использовать собственный объявленный Node version.
- В P26 validation workflow заменены `actions/checkout@v4`/`actions/setup-node@v4` на `@v7`.
- Успешный результат 6/6 в разделе выше относится к исходной ревизии CI-hardening до этих адаптаций. **Обновлённый набор из шести тестов на этой интеграционной версии ещё не запускался**: GitHub Actions по-прежнему завершает задания до первого шага. Выполнена только статическая проверка содержимого и условий конфигурации; это не заменяет `node --test` на точном финальном SHA.

## Повторная проверка на интеграционной ветке (2026-10-26, WorkPass428)

На consolidation head `badc4401ca546d2d92c59f3d381b08da07a803d1` наблюдается та же сигнатура, что была описана выше: workflow runs завершаются `failure`, но job records не содержат поля `steps`, поле `logs_url` равно `null`, а запросы job-step/job-log возвращают `BlobNotFound`. Это уже не единичный workflow.

Текущий видимый набор из 14 runs:

- HMX canonical apply: [40350709518](https://github.com/ailtron1ss-rgb/NK1/actions/runs/40350709518), job `121669681500` — `failure`, 0 доступных шагов, `logs_url=null`.
- Core regression: [40350709589](https://github.com/ailtron1ss-rgb/NK1/actions/runs/40350709589), job `121669681302` — `failure`, 0 доступных шагов.
- P26 validation: [40350709562](https://github.com/ailtron1ss-rgb/NK1/actions/runs/40350709562), job `121669681157` — `failure`, 0 доступных шагов.
- Continual-learning metrics: [40350709573](https://github.com/ailtron1ss-rgb/NK1/actions/runs/40350709573), job `121669681064` — `failure`, 0 доступных шагов.
- Остальные видимые задания этого head — WorkPass79/99/102/105/108/287-288/291-294/292-293 — также завершились `failure`.

Диагностический вывод ограничен тем, что реально наблюдается: задания завершились до доступного шага и logs API не возвращает логи. Это согласуется с проблемой старта runner/account-level execution, но текущие данные не содержат annotation или runner metadata, поэтому конкретную причину (в том числе billing lock) нельзя считать подтверждённой.

Следствие для разработки: не интерпретировать массовые zero-step `failure` как результаты отдельных TypeScript или HMX тестов. Последний проверяемый source/test snapshot остаётся непроверенным исполнением на hosted runner; любые кодовые проверки здесь отмечаются как статические, если нет успешного тестового запуска.
