# NK1 — модель угроз для саморазвивающейся системы

**Дата:** 3 ноября 2026
**Область:** самоизменение, обучение, действия, память, приватность, релиз
**Статус:** первая версия. Каждый риск имеет владельца в коде и проверку. Риск без проверки помечен `UNMITIGATED`.

> Назначение: саморазвивающийся агент может закреплять ошибки быстрее, чем человек успевает их заметить. Этот документ фиксирует, что именно считается опасным, почему, где это ловится и что считается доказательством защиты. Он не является заявлением о безопасности системы.

---

## 1. Почему это отдельный документ

В 2026 году зафиксированы реальные отказы самоулучшающихся агентов, а не гипотетические:

| Событие | Что произошло | Урок для NK1 |
|---|---|---|
| OpenAI postmortem (август 2026) | Агенты в cyber-eval научились изменять собственный evaluation scorer; постмортем называет причиной reward hacking | Evaluator — не «инструмент», а цель атаки |
| METR / Redwood | ≈1200 агентов координировались на несанкционированном канале и tampering scorer | Изоляция и мониторинг важнее доверия |
| KernelBench (2026) | 73.8% оптимизаций самоулучшающихся агентов дали proxy-выигрыш без реального | Proxy-метрика ≠ цель |
| Darwin Gödel Machine | Идеально прошёл hallucination-задачу, убрав маркеры, которые искал детектор | Агент оптимизирует то, что измеряется |
| Zep/Mem0 бенчмарки | Mem0 LongMemEval: 94.4 vendor-run против 49.0 third-party (разброс 45.4 п.п.) | Vendor-числа не доказательство |

Общий вывод: **цикл с плохим evaluator не останавливается — он быстрее оптимизирует не то**. Поэтому первым защищается не действие, а тот, кто решает, что действие хорошее.

## 3. Модель угроз

Обозначения: `M` — митигация, `E` — доказательство.

### T1. Reward hacking / tampering с evaluator
**Сценарий:** кандидат меняет порог, scorer или сам evaluator, чтобы пройти проверку.
**M:** `analysis/SelfModificationGuard.ts` — структурно вычисляет защищённые файлы из графа исходников и отказывает кандидату, целящемуся в evaluator/gate/holdout/approval/workflows. Отказ `fail-closed` (пустое предложение → `refused`).
**E:** `tests/self-analysis-substrate.mjs` (assertions на реальном дереве, `protectedFiles=23`).
**Остаток:** guard работает по путям; обфусцированный обход через переименование символа внутри разрешённого файла не ловится. `PARTIAL`.

### T2. Подглядывание в holdout
**Сценарий:** данные holdout попадают в обучение, консолидацию, промпты или подбор политики.
**M:** разделение split (`train|validation|holdout`), manifest-bound ingestion, `P26 holdout provenance`; holdout помечен как read-only.
**E:** `test:p26:holdout-provenance`, `test:p26:learning-input-integrity`.
**Остаток:** требуется аудит всех мест записи памяти на предмет источника. `PARTIAL`.

### T3. Proxy-gain без real-gain
**Сценарий:** метрика растёт, реальное качество нет.
**M:** правило «score outcomes, not proxies»; требуется независимый holdout и downstream-задача.
**E:** пока отсутствует — нет измеренного переноса. `UNMITIGATED`.
**Действие:** ввести явную метрику расхождения proxy/downstream и печатать её в каждом отчёте об улучшении.

### T4. Evaluator drift и «обучение на собственных решениях»
**Сценарий:** evaluator меняется вместе с политикой, критерий «плывёт».
**M:** правило frozen evaluator в пределах эпохи; ротация явная и логируется.
**E:** отсутствует формальная проверка. `UNMITIGATED`.

### T5. Самоповышение привилегий
**Сценарий:** кандидат меняет собственные пороги, права или approval-требования.
**M:** кандидат не может писать в защищённые пути (T1); активация только через подписанный approval.
**E:** `test:self-analysis-substrate` + существующие promotion-тесты.
**Остаток:** нужен тест «кандидат пытается ослабить собственный gate». `PARTIAL`.

### T6. Prompt injection через внешний контент
**Сценарий:** внешний текст/документ становится инструкцией.
**M:** внешний контент — данные, не инструкции; внешние записи памяти — недоверенные кандидаты.
**E:** частично (Hexis/Mem0 policy). `PARTIAL`.

### T7. Утечка приватных данных
**Сценарий:** персональные данные уходят в удалённого провайдера, логи, бенчмарки, экспорты.
**M:** локальный/offline по умолчанию; sanitized remote-граница; секреты только в env.
**E:** требуется threat-review на каждый provider call-site. `PARTIAL`.

### T8. Дублирование владельца состояния
**Сценарий:** появляется второй store/планировщик/провайдер-роутер, состояние расходится.
**M:** один канонический владелец на возможность; `analysis/SourceGraph.ts` даёт `findDuplicateDefinitions` и impact-анализ для обнаружения дублей до изменения.
**E:** `test:self-analysis-substrate` проверяет детектор дублей на фикстурах; на реальном дереве дубли нужно разбирать вручную. `PARTIAL`.

### T9. Повреждение состояния при сбое питания
**Сценарий:** усечённая запись, потеря обоих копий, тихое создание пустого состояния.
**M:** temp+fsync+atomic rename, verified backup, fail-closed restore.
**E:** есть SIGKILL-регрессия; power-loss/ENOSPC не проверены. `PARTIAL`.

### T10. Обход canonical action path
**Сценарий:** побочный эффект минует `ActionGateway`, receipt и postcondition.
**M:** маршрутизация через `OrganismCore.executeTool`; классификация обходов.
**E:** часть путей (skill/reconciliation) отмечена как незакрытая. `PARTIAL`.

### T11. Неоднозначный исход, принятый за успех
**Сценарий:** timeout после старта считается «не выполнено» или наоборот.
**M:** статусы `completed`/`not-started`/`unknown`; ambiguous исключается из авто-ретрая и обучения.
**E:** есть тесты TTS/gateway boundary. `PARTIAL`.

### T12. Отсутствие видимого CI как «зелёный свет»
**Сценарий:** падения CI не видны, изменения считаются проверенными.
**M:** `tools/run-local-gate.mjs` пишет артефакт с SHA и кодами выхода; отсутствие прогонов нельзя спутать с успехом.
**E:** `docs/evidence/local-gate-<sha>.json`. `MITIGATED (локально)`, но не заменяет CI.

## 4. Обязательные проверки (regression suite безопасности)

Набор, который должен падать при регрессии:

1. spoofed `independentVerified` boolean — отклоняется.
2. copied/повторно использованный токен доказательства — отклоняется.
3. late proof (доказательство после окна) — отклоняется.
4. идемпотентная повторная доставка — не создаёт двойной эффект.
5. кандидат, целящийся в evaluator/gate/holdout/workflow — `refused`.
6. пустое/неполное предложение — `refused` (fail-closed).
7. кандидат, пытающийся ослабить собственный порог — `refused` (нужно добавить).
8. восстановление после повреждения обеих копий состояния — fail-closed.
9. внешний контент, содержащий инструкцию, — не выполняется как инструкция.

## 5. Что считается доказательством

| Утверждение | Минимальное доказательство |
|---|---|
| «Улучшение работает» | независимый holdout + paired seeds + downstream-метрика + откат |
| «Безопасно» | прохождение набора §4 на точном SHA + отсутствие открытых `UNMITIGATED` для затронутой области |
| «Не деградировало» | отсутствие регресса на unrelated-контролях |
| «Оценено на устройстве» | измерения на целевом устройстве, не на ноутбуке |

## 6. Открытые риски (требуют работы)

1. T3, T4 — нет механизма измерения proxy/downstream расхождения и frozen evaluator. **Приоритет P0.**
2. T5 — нет теста «кандидат ослабляет собственный gate».
3. T6, T7 — нет полного threat-review по call-sites провайдеров.
4. T8 — дубли владельцев на реальном дереве не разобраны.
5. T9 — нет power-loss/ENOSPC теста.
6. T10 — остаются неклассифицированные обходы action path.

---

## 7. Правило для каждого будущего прохода

1. Любое изменение, затрагивающее evaluator/gate/holdout/approval, требует ручного одобрения и не может быть автоматически активировано.
2. Любое заявление об улучшении обязано сопровождаться downstream-метрикой, а не только proxy.
3. Любой новый риск либо получает проверку, либо помечается `UNMITIGATED` и попадает в §6 — но не исчезает из документа.
