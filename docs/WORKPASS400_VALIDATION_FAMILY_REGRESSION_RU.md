# WorkPass400 — регресс целого семейства задач в проверке обучения

## Задача

WorkPass399 блокировал сильный регресс отдельной validation-задачи, но оставлял тонкую лазейку: несколько задач одного семейства могли ухудшиться умеренно — каждая ниже старого порога 0,20, — а улучшения другого семейства увеличивали общий macro-score. Такой кандидат мог бы пройти promotion gate, хотя практическая способность внутри определённого домена ухудшилась.

## Изменение в NK1

В `SkillLearnBenchAdapter.ts` добавлен общий агрегатор попарных дельт по семействам задач. Сначала повторные trials усредняются внутри одной задачи; затем задачи одинаково взвешиваются внутри семейства. Количество повторов не может искусственно увеличить вес семейства.

Новые параметры gate:

- `maximumValidationFamilyRegression01` — допустимый validation-регресс семейства; значение по умолчанию 0,10.
- `minimumValidationFamilyTasks` — число разных validation-задач, необходимое для семейного veto; по умолчанию 2.

В отчёт добавлены `validationFamiliesEvaluated` и `validationFamilyRegressions`. Новый отказ имеет код `validation-family-regression-exceeds-tolerance`; обратная связь не раскрывает имя семейства или его holdout-оценки. Старый holdout family-gate использует тот же агрегатор, чтобы избежать двух разных реализаций вычисления семейных дельт.

Некорректные значения порогов отвергаются с ошибкой, а не исправляются автоматически. При отсутствии метаданных `taskFamily` код не выводит семейства из названий задач и сохраняет прежнюю совместимость.

## Регрессионный сценарий

Тест P29 задаёт два семейства: в первом несколько задач проседают на 0,16 каждая — ниже per-task threshold 0,20; во втором задачи существенно улучшаются. Macro-average в целом растёт, но оба семейства имеют достаточное покрытие, поэтому новый семейный gate блокирует продвижение. Тест также проверяет, что счётчик per-task regression остаётся нулевым и что `NaN` в новом параметре отвергается.

## Исследовательская мотивация

[SkillLearnBench](https://arxiv.org/abs/2604.20087) проверяет качество навыка, траекторию исполнения и результат задачи на 20 верифицированных задачах из 15 поддоменов и сообщает, что приросты continual learning непостоянны между задачами и моделями. Поэтому одной усреднённой метрики недостаточно: нужна проверка локальных регрессий на уровне задачи и семейства.

[Hermes Agent Self-Evolution](https://github.com/NousResearch/hermes-agent-self-evolution) отделяет генерацию кандидата от набора ограничений, тестирования и рассмотрения изменения. NK1 адаптирует сам принцип gate и независимой оценки, а не копирует сторонний runtime.

## Границы и состояние проверки

- 0,10 и минимальное покрытие в 2 задачи — инженерные стартовые значения NK1, не универсальные научные константы.
- До решения о production promotion нужны фиксированный набор задач, несколько seed-пар, оценка дисперсии, bootstrap/доверительные интервалы и проверка стоимости измерений.
- Сценарий и код закоммичены на `feature/learning`; тесты и typecheck пока нельзя считать прошедшими: доступные GitHub Actions завершались без доступного списка steps/logs.
- Используется существующая зависимость и существующий P26/P29 workflow; новая runtime-зависимость и дублирующий workflow не добавлены.

## Следующий проход

1. Добавить оценку шума на paired seeds, чтобы разница внутри порога не выдавалась за надёжное изменение.
2. Протоколировать версию manifest, seed, семейства и число пар для каждого evaluation report.
3. Подключить результаты к непрерывному журналу развития навыка и ростовой кривой, не позволяя обучающему оптимизатору читать holdout-примеры или holdout-оценки.
